## Changes in this Version

This section covers July and August 2026, the period in which the system took its current shape.
Earlier changes have not been lost: the About page keeps a dated snapshot of this document for every
revision, so selecting an older version from the dropdown shows both what the system did at that time
and what had just changed. Everything those earlier entries described that is still true is documented
in the numbered sections below.

### How Fred runs

- **The resolution machine now actually runs — on a schedule, with its spending on the books.** An August 2026 audit of the machine's six build phases found that, although the machine was complete and well-tested, nothing ever ran it: no scheduled job invoked it, its tables never existed in the production database, the base-rate block built for the forecasting prompts therefore always rendered as nothing, and the money its document-reading step spends was invisible to the Costs page. That is now fixed, in three parts. *First, a monthly live run*: the monthly data refresh on the 28th gained a step that runs the machine over the three most recent months for cyclones, floods and drought — recent months stay provisional until their 60-day freeze, so each monthly pass revises the still-open months and leaves settled ones alone. *Second, a nightly history builder*: a new scheduled job works through the machine's multi-decade replay (cyclones from 2000, floods from 2010, drought from 2017) in bounded nightly chunks, picking up each night exactly where the last stopped, until the history — and the base rates the forecasters are shown — is complete; after that it becomes a near-instant nightly no-op that simply keeps the record rolling forward. *Third, honest bookkeeping and diagnostics*: every document-reading AI call now lands in the same cost ledger as everything else (a new "PA resolution" line on the Costs page), the run summary and database inspection reports gained sections showing exactly what the machine assessed, graded and spent, and each run writes a machine-readable summary file so a failure can be diagnosed from artifacts rather than expired logs. One important boundary is unchanged and deliberate: **the machine's answers do not yet grade any forecast.** It runs in shadow mode — producing grades, base rates and a monthly scorecard alongside the current IFRC-based grading — until its first scorecards justify the switch, which will be its own deliberate change.
- **The audit also hardened the machine before its first real run.** The most important fixes: a document whose AI reading failed once was cached as failed forever (a brief provider outage could permanently blind the machine to those documents — failures are now retried on the next run, and calls that never actually happened no longer eat the monthly spending allowance); a document shared between two hazards or two countries could have one cell's answer silently reused for the other's question (the reading cache is now scoped to the exact question asked); the reading prompt told the model to ignore "other time periods" without ever saying which period was meant (it now names the month, and the country by name rather than by code); a transcribed figure only had to arrive with a real sentence from the document, not one that actually contained the number (the number must now appear in its quoted sentence); one country's error could abort the whole month and every month after it (each country now fails alone and is retried next run); and still-revisable provisional grades were leaking into the severity base rates shown to forecasters (only frozen grades count now).
- **Core data is now refreshed days before the forecast, not two weeks after it.** The monthly ingestion of the sources Fred later scores its forecasts against — conflict fatalities, disaster impacts, displacement, food insecurity — ran on the 15th, while the forecast itself runs on the 1st. Each month's forecasts were therefore reasoning over core data that was already more than two weeks old, and that month's refresh landed too late to help. Ingestion moved to the 28th, so forecasts now run on data less than four days old and on calibration weights recomputed three days earlier. The accepted cost is that each month's ground truth is confirmed about thirteen days later than before, which does not affect what any forecast is scored against.
- **The pipeline can now run in stages to cut model costs roughly in half — with identical forecasts.** All the big AI providers offer a "batch" service: hand them a large stack of independent requests, let them process it within a day, and pay half price on every token, both input and output. Fred's monthly cadence makes that trade ideal, so the system gained an alternative staged way of running: the risk-scan and forecasting steps now can pause after preparing their model requests, submit them as a batch, and a small watcher resumes the pipeline automatically when the providers finish — typically within the hour, worst case a day per stage. Each stage starts that watcher as soon as it has submitted its batch, and the watcher then re-checks every few minutes until the work is done; a scheduled job also runs as a backstop in case a hand-off is ever missed. The requests sent in a batch are byte-for-byte identical to what the always-available immediate mode would send — same models, same settings, same prompts — so the forecasts themselves do not change; any request a batch fails to answer is automatically re-asked the normal way, so a run always completes. On top of batching, the prompts were reorganized so that their fixed instructions come first and the per-country data last, which lets providers recognize and discount the repeated portion ("prompt caching") — and Sibyl's step-by-step research conversations now reuse their repeated context the same way. The Costs page bookkeeping understands all of this: batched and cached tokens are billed at their true discounted rates instead of full price. As of late July 2026 this is the production setup: the monthly run now enters through the staged pipeline, and the prompt reorganization and caching are switched on. The old single-job immediate mode remains available as a manual fallback, and a comparison harness checks the first staged cycles against the last conventional run to confirm the forecasts are statistically indistinguishable.
- **Three of the five forecasting models upgraded — and their "thinking effort" settings now actually take effect.** The ensemble moved to OpenAI's GPT-5.6 Sol and GPT-5.6 Luna and Anthropic's Claude Opus 5, replacing GPT-5.4, GPT-5.4 Mini and Claude Opus 4.8 (the two Google models are unchanged). While making the change we found that the per-model "thinking effort" settings written in the configuration file were being discarded before the request reached the provider: the two OpenAI models had been running at their default effort rather than the configured one, and Gemini Pro had been running with no thinking level set at all despite the configuration asking for medium. Those settings now reach the models as written, so the ensemble reasons at the depth it was configured to. Two further changes were needed for the new Anthropic model: it refuses requests that carry the older "temperature" setting (which would have caused every Claude forecast *and* the whole Sibyl deep-research track to fail outright), and it now thinks before answering by default, drawing on the same output budget as the answer itself — so that budget was doubled to keep long forecasts from being cut off mid-answer. The system also now reports explicitly when a model declines a request on safety grounds or runs out of output room, instead of that model quietly disappearing from the ensemble. **Cost note:** the frontier OpenAI slot is roughly twice as expensive per token as before, the small OpenAI model is about a third more, and the Anthropic model's per-token price is unchanged (though its new default thinking adds some output tokens) — expect a modest rise in per-run spend on the Costs page.
- **New model lineup across the whole system, and three providers retired.** *(The lineup named here was superseded later in July — see "Three of the five forecasting models upgraded" above. The provider retirement and the cost-bookkeeping changes still stand.)* Fred's forecasting ensemble was refreshed to five models from three providers: GPT-5.4 and GPT-5.4 Mini (OpenAI), Claude Opus 4.8 (Anthropic), and Gemini 3.1 Pro and Gemini 3.5 Flash (Google). The Kimi and DeepSeek models were removed from the ensemble, and support for xAI, Kimi, and DeepSeek was removed entirely. All Horizon Scanner work (triage and regime-change assessment), the lighter Track 2 forecasts, and scenario writing now run on Gemini 3.5 Flash; Sibyl continues to use Claude Opus 4.8. Each model's "thinking effort" was tuned for the best cost/quality balance, and a bug was fixed that had silently prevented Gemini 3.1 Pro from using its configured thinking level. Cost bookkeeping was also overhauled: prices are now recorded per million tokens (the industry standard) instead of per thousand, every rate was checked against current provider pricing (one outdated rate was corrected), and forecasts are now always labeled with the exact model that produced them (for example "gemini-3.5-flash") rather than generic names like "Gemini Flash" — on the dashboard, in downloads, and in the accuracy-tracking tables.
- **Large internal reorganization, no behavior change.** The two biggest pieces of code (the forecasting runner and the dashboard's data service) were split into smaller, focused modules, and the system's data-merging rulebook was reduced from two overlapping implementations to one. The dashboard service also gained a small self-healing step: if its database connection breaks mid-request, it reconnects and retries once instead of failing. The system now also keeps a queryable map of exactly which countries and months each data source covers (used to decide when "no data" safely means "nothing happened"), and forecast-bucket calibration data is now stamped with the bucket layout it was learned under, so a future change to the buckets can never silently reuse stale calibration.

### What the forecasting models are shown

- **The resolution machine now tells the forecasters the rule it will grade them by.** Its sixth and final phase closes the loop the previous five opened. Every people-affected question about a cyclone, flood or drought now carries a short block in its forecasting prompt containing what the machine learned from replaying history — how often that hazard has occurred in that country in each of the six months being forecast, how large it has been when it did occur, and which sources those figures came from — followed by two plain sentences describing exactly how the question will be graded: what counts as the hazard happening, what makes a quiet month a confident zero rather than an ungraded one, which reporting sources are consulted and in what order, and that the answer freezes 60 days after month-end. A forecaster that does not know the grading rule is guessing at the target as well as at the world. Those two sentences are written from the rulebook each time a prompt is built rather than typed into the prompt, so changing a threshold changes what the models are told on the next run with nothing to keep in step by hand — a prompt still describing last quarter's rules would be confidently wrong, which is worse than one describing no rules. The block is shown only for people-affected questions on the three hazards the machine grades, because food-crisis questions ask about a different quantity; a country with too few graded events states how many it has rather than showing a percentile spread that two events cannot support; a country the machine has never examined gets no block at all rather than one implying an empty record; and the whole thing is held to roughly 200 words, since space spent here is space taken from current evidence. Drought carries an explicit warning that its record is only about eight years deep and patchy by country.
- **Expert assessments and counter-evidence now actually reach the forecasters.** Two inputs that were being collected but silently never shown to the forecasting models now appear in their prompts: ICG CrisisWatch's monthly expert assessments (for conflict questions) and the fresh web-search evidence gathered during the risk scan. In addition, the devil's-advocate counter-evidence produced for every elevated-risk case is now injected for all of those cases — previously it was only shown at the highest alert levels, so in typical runs it was paid for but never used.
- **Hazard "tail packs" retired.** The separate tail-pack evidence feature was removed: the counter-evidence checks above now cover its role for every elevated-risk case, and the risk scan's search evidence reaches the forecasters directly. This removes duplicated searching without losing any input.
- **Food-crisis history restored in forecasting prompts.** Every food-security (IPC Phase 3+) forecast prompt had been telling the models "no historical data exists for this country" — even for countries with years of FEWS NET assessments — because of a database-connection conflict that failed silently. The models now see the real history again, and if the loader ever fails it says "history unavailable this run" instead of pretending the record is empty.
- **Wrong-country political events removed from forecasting prompts.** A review of a July 2026 test run found that the "key political events" shown to the forecasting models were the same ~50 global events for every country — Somalia's conflict forecast, for example, was being shown protests from Iran and arrests from Ecuador. The cause: the events provider ignores an unsupported country filter and returns worldwide events, which were then stored under whichever country had been requested. Events are now attributed by the country stamped on each event itself, a guard refuses to store an event under the wrong country, and the contaminated table is wiped and refetched automatically.
- **Recent-trend figures no longer count the current, incomplete month.** A forecast run early in the month used to treat the month's first few days as a full month of data — making conflict look like it was sharply de-escalating when the month simply wasn't over yet. Trend and "last month" figures now stop at the last complete calendar month.
- **RC and triage now run a single assessment pass by default (July 2026).** The system previously asked the same model the same question twice and averaged the answers. Because both passes used identical settings, the second answer was always a word-for-word copy of the first — doubling the cost and time of every scan for no benefit. Each hazard now gets one RC pass and one triage pass by default; the two-pass machinery remains available by configuration for setups where a second, genuinely different opinion is wanted — it only adds signal when the second pass uses a different model.
- **Ungrounded hazards are now truly held back from forecasting (July 2026 fix).** When the web-search budget runs out mid-scan, the system blocks any hazard that never received fresh search evidence from being forecast. A gap meant high-priority hazards slipped past this block and were forecast anyway on stale information; that gap is closed — a hazard with no grounding evidence is now skipped for the month regardless of how high its risk score is, rather than producing a forecast built on incomplete inputs.

### Forecast and scoring correctness

- **Forecasts now cover exactly the months each question asks about.** A July 2026 repair fixed a serious misalignment: since late March 2026, the forecasting models had been asked to predict the six months *after* each question's stated window rather than the window itself (a knock-on effect of an earlier fix that changed what the "target month" field means). Every part of the pipeline — the prompts sent to models, the stored monthly forecasts, and the scoring against observed outcomes — is now anchored to the first month of the question window. Safeguards were added so a forecast whose months don't line up with its question is rejected rather than silently accepted, and a model that returns a month outside the window has that month discarded instead of shifting all its other months. Forecasts and scores produced during the misaligned period were archived; the system starts fresh from the July 2026 run.
- **Every magnitude forecast now has a dedicated "zero impact" bucket, and fatalities gained a 1,000+ bucket.** Previously the lowest forecast bucket lumped "nothing happened" together with "a small event happened" (for example, "fewer than 10,000 people affected" covered both a quiet month and a real but modest flood). Each metric now has an explicit bottom bucket meaning exactly zero — 0 people affected, 0 conflict fatalities, or 0 people in food crisis — and the next bucket starts at 1. This lets the models say clearly how likely it is that nothing happens at all, and it makes the expected-impact calculation treat "no impact" as genuinely zero. People-affected and food-crisis questions now use six buckets, and conflict-fatality questions use seven, including a new top bucket for months with 1,000 or more deaths (previously everything above 500 was a single bucket). The change applies from the fresh July 2026 restart, so all stored forecasts use the new buckets consistently; a safeguard skips (rather than mis-scores) any forecast made under the old bucket layout if an old database copy ever resurfaces. In passing, this work also fixed a dormant bug in the calibration-advice diagnostics that had been sorting observed outcomes one bucket too high.
- **Accuracy scores now use the standard textbook formula.** The distribution-accuracy score (shown as CRPS on the dashboard) previously used a non-standard divisor that made all values read about 20% lower than the standard form found in the forecasting literature. It is now the standard normalized Ranked Probability Score: 0 means a perfect forecast, 1 means the worst possible one, and values are directly comparable to published benchmarks. This change took effect together with the fresh July 2026 restart, so all stored scores are on the new scale.
- **Ground truth is chosen by source authority, not arrival order.** When several data sources report different figures for the same country and month (for example, an IFRC "people affected" total alongside a displacement-only count), the system previously kept whichever row happened to be ingested last — which could swing the recorded outcome by enormous margins between runs. It now picks deterministically: direct "people affected" figures beat displacement components, higher-authority publishers (IFRC, ACLED) beat others, and recency only breaks ties. Each resolution also records which source won.
- **Months with no data are no longer scored as "nothing happened."** For sources where absence normally means zero (ACLED conflict fatalities, GDACS disaster alerts), the system now first checks that the source actually reported anything at all for that calendar month. If a month is missing from the source entirely — an ingestion failure or a gap before coverage began — forecasts for that month simply remain unscored instead of being treated as if zero people were affected.
- **No more false "zero casualties" for countries outside a source's coverage.** When the conflict-fatalities source (ACLED) has no record for a country and month, the system treats that as "zero deaths" — which is right for countries ACLED covers, but wrong for a country ACLED has never reported on at all. The system now checks that a country appears somewhere in the source's history before assuming absence means zero; countries the source has never covered are left unscored instead. Disaster-alert questions (GDACS) deliberately keep the old behavior, because that source watches the whole planet from satellite data — no alert genuinely means no event.
- **Source priority rules are now actually applied when merging overlapping data.** A July 2026 code audit found that the written policy for choosing between data sources — IFRC and ACLED first, then IDMC, with ties going to the freshest, most complete figure — was silently not being applied in the main data pipeline. Because of a naming mismatch, IFRC (the primary source for people affected by floods, droughts, and cyclones) was being treated as the *lowest*-priority source, and when two sources tied, the winner was picked essentially alphabetically — a stale or even empty figure could beat a fresh, real one. The configuration and the merging engine now agree: the documented priority order applies, fresher figures win ties, and a row with an actual value always beats one without. Recorded facts written before this fix may have had the wrong winner; the next full data refresh rewrites them under the corrected rules.
- **Past accuracy now feeds back into the ensemble.** The system has long computed per-model calibration weights from historical scores, but the forecaster never actually used them. Ensemble forecasts (both the averaging and Bayesian combination methods) now weight each model by its calibration weight, so models with better track records on a given hazard and metric count for more. Weights are also now computed only over the individual models — the combined ensemble's own scores no longer compete against the models it is built from, which had been distorting the weights.
- **Binary event scoring made deterministic.** The score recorded for a binary event forecast (e.g., "will a significant flood occur?") now always comes from the ensemble's averaging method, rather than depending on the order rows happened to be written to the database. A follow-up went further: every score is now filed under an explicit model name (individual models and the combined ensembles alike), removing a duplicate "unnamed ensemble" score that could be double-counted in averages.
- **Very rare events can now receive appropriately tiny probabilities.** Model probabilities for binary event questions were previously floored at 1%, which penalized models for correctly judging that, say, an off-season cyclone is far less likely than that. The floor is now 0.1%, and the prompts tell models the new bounds.
- **Incomplete AI answers to yes/no event questions are now rejected.** When a model asked for six monthly probabilities returned only some of them, the partial answer used to flow into the combined forecast, quietly leaving gaps in the stored months. A model that skips months now has its whole answer discarded for that question, and the system never records a partial set of months — matching the strictness the magnitude forecasts already had.
- **The Bayesian combination of yes/no event forecasts now actually gets saved.** A follow-up to the July 2026 audit found that whenever more than one AI model answered a yes/no event question (will a significant flood/cyclone/food-crisis event occur?), a coding slip caused the system's second, Bayesian way of combining their answers to crash quietly every time — only the simple average was ever stored. The crash is fixed, both combination methods are now saved, and a new test permanently guards this. Accuracy scoring for these questions always used the simple average, so past scores are unaffected.

### New capabilities

- **New: Sibyl, a second, independent forecasting track built on deep web research.** Alongside the standard pipeline — which reasons over the structured data feeds Fred ingests in bulk — the system now runs a parallel "oracle" called Sibyl for the ten most volatile people-affected and conflict-fatality questions of each run. For each of those questions, an AI research agent (Claude Opus) conducts its own open-web investigation: it searches, reads sources, and updates a running estimate step by step, exactly the way a human superforecaster would reconcile the historical base rate with fresh evidence. Three independent investigations are run per question and their distributions are pooled, which automatically widens the forecast when the investigations disagree. By design, the only input Sibyl shares with the standard track is the historical base rate from Fred's own database — everything else it discovers itself, and it is blocked from reading the data sources used to grade the forecasts. Sibyl's forecasts are stored beside the standard ones and scored head-to-head by the same accuracy loop, and a new dashboard page shows, for every question, how far the two tracks disagree (and each investigation's full reasoning trail). The whole run is protected by a hard spending cap (default $40): if reached, the least-volatile remaining questions are skipped and the run is clearly flagged.
- **Sibyl now works on test runs.** The deep-research track was silently skipping every test-mode pipeline run because test-run questions are hidden from production queries and Sibyl didn't know the run was a test. It now detects that the run it is forecasting was a test run, opts into test mode itself, and labels its own outputs as test data. Its pre-run check also logs exactly which questions were and weren't eligible, so an empty run explains itself.
- **New: a "resolution machine" for people-affected ground truth (first phase: tropical cyclones).** Today, "people affected" questions for floods, storms, and droughts can only be graded when the IFRC has published a matching field report — which happens for only a few percent of country-months, so most such forecasts are never scored. A new, separate resolution machine addresses the most common case first: months where **nothing happened**. For every country and month it checks the official global storm-track archive (IBTrACS) for any tropical-storm-strength track passing within 200 km of the country's territory; if none did, and a sweep of ReliefWeb's humanitarian reporting for that country and month also finds no cyclone coverage, the month is graded as a confident zero — with the full evidence of absence (the storm-track query, the report searches and their hit counts, and timestamps) stored alongside. If reporting IS found despite no track, the month is flagged for impact grading instead (a later phase will walk a fixed ladder of reporting sources — EM-DAT, figures stated in ReliefWeb documents, IFRC field reports, and displacement counts — to pick a number). Every decision rule and threshold lives in a single reviewable rulebook file; grades freeze 60 days after month-end and are never silently rewritten (later revisions are logged separately); and zeros are refused whenever the storm archive demonstrably hasn't caught up with the month yet, so a data gap can never masquerade as a quiet month.
- **The resolution machine now covers floods, and can put a number on a month, not just a zero.** Its second phase adds the other half of the job. **Floods are now detected** the same way cyclones are, using GDACS disaster alerts: a country-month counts as flooded when a GDACS flood alert for that country reaches orange or red, and quiet flood months get the same ReliefWeb silence check and the same confident zero. **And when a hazard *did* happen, the machine now grades it.** It walks a fixed, published ladder of reporting sources — EM-DAT first, then figures stated in ReliefWeb documents (arriving in the next phase), then IFRC field reports, then IDMC displacement counts — and takes the figure from the highest rung that has one. Four rules govern what happens next, and all four are deliberate. *Displacement is a floor, not an answer*: an IDMC figure is published explicitly as "at least this many", because displaced people are only a subset of those a flood affects. *A sanity check flags, it never rewrites*: if the chosen figure exceeds what GDACS estimates was even exposed to the hazard, or exceeds the country's population, or if two adjacent rungs disagree by more than tenfold, the figure still stands — the ladder decided it — but the month is flagged for a human to look at, rather than being quietly replaced with a different source's number. *A figure is never split across months*: an event spanning a month boundary is detected in both months, but its reported total is credited entirely to the month it began, because splitting it would invent a monthly breakdown no source ever published (the event's full span is recorded alongside, so this is always visible). *Waiting is not the same as not knowing*: if no source has reported a figure yet and the 60-day freeze deadline hasn't passed, the machine records nothing at all rather than grading the month "no data" — EM-DAT routinely publishes weeks after an event, and an early "no data" would record impatience as a finding. Only once the deadline passes with still no figure is the month graded "no data" and flagged for review. Grades written before the deadline are marked **provisional** and may still improve; from the deadline they are final. Throughout, a source that couldn't be reached is recorded as *unread*, never as *empty* — the distinction matters, because only genuine silence can justify a zero.
- **The resolution machine now reads the reports, not just the databases.** Its third phase fills the gap that the first two exposed: most floods and storms never reach EM-DAT and never get an IFRC field report, but somebody — a national disaster agency, an OCHA situation report, a Red Cross update — almost always publishes a sentence with a number in it. For a country-month where a hazard *was* detected and no higher-ranked source has already answered, the machine now fetches up to thirty of the most authoritative recent ReliefWeb documents (OCHA first, then governments, then UN agencies) and has a cheap AI model read each one. **Its only job is transcription.** It is instructed to copy out every people-affected figure the document explicitly states, together with the exact sentence containing it, and it is forbidden to estimate, to convert units, to add figures together, or to use anything it happens to know that the document does not say. If a document states no figure, the correct answer is none — and that is a common, expected outcome. Crucially, the instruction is not what enforces this. Every extracted figure must arrive with a quote, and that quote must actually be found in the document; a figure whose sentence cannot be located is discarded and the reason recorded. To invent a number, the model would have to invent a sentence that is already in the text. Everything a figure could be *turned into* then happens by fixed rule, with no AI involved: a figure given in households is multiplied by a published, per-country household size and the conversion is recorded so anyone can undo it; the same statement repeated across five situation reports collapses to one; a figure larger than the population GDACS estimates was even exposed to the hazard is rejected as a likely mis-transcription; and when several bodies quote different totals for one flood, the machine prefers the most authoritative attribution — government, then UN agency, then Red Cross or NGO, then media — and the most recent figure within that tier, rather than simply taking the biggest number. Every surviving figure is stored with its quote, its source document, and the model that read it. **This is the only part of the whole machine that costs money**, so it is guarded three ways: a cap on documents per country-month, a hard cap on AI calls per calendar month that is shared across every run rather than reset by each one, and a rule that skips any month a higher-ranked source has already settled. Documents that have been read once are cached, so re-running a month is free. Running out of budget is recorded on the month as *unread documents*, never as *nothing was reported* — the same distinction the machine draws everywhere else. At current settings the expected spend is around fourteen dollars a month; every other data source it uses is free.
- **The resolution machine now grades drought, by a different rule from everything else.** Its fourth phase covers the one hazard with no event: nothing makes landfall and no alert turns orange, so there is no day on which a drought "happens". What exists instead is the IPC/CH food-security analysis cycle, and drought now resolves from it directly, skipping the reporting ladder entirely. For each country-month the machine takes the **increase** in the population classified at IPC Phase 3 or above between one analysis and the one before it, floored at zero — the people who newly fell into crisis-level food insecurity. Two design choices carry the weight. First, **attribution**: IPC publishes how many people are in Phase 3+ but never says why, because the driver is discussed in narrative reports rather than in any data field — so an increase is only published as *drought* impact where an independent agricultural-drought indicator agrees the country was in drought. Without that check, conflict- and price-driven hunger would be recorded as drought impact and would corrupt the ground truth these forecasts are graded against; where an increase is real but unattributable, the machine publishes no drought figure at all and flags the month. Second, **months**: an IPC analysis is valid across several months but states a single figure, so the machine publishes that increase for every month the analysis covers — the people who fell into crisis remain in crisis for its duration — and every grade states on its face that these are standing totals which must never be added together across months. The same two signals decide a drought zero: no indicator signal and no Phase 3+ deterioration together justify a confident zero, while an indicator that could not be *read* suppresses the zero rather than permitting it — the machine will not turn its own outage into a finding. Two situations are deliberately refused rather than guessed: a country whose first analysis has no predecessor to compare against is graded "no data", because that figure is a standing total rather than the month's newly affected and publishing it would overstate by the entire pre-existing caseload; and a month with indicated drought but no IPC analysis published by the 60-day freeze deadline is graded "no data" and flagged for review. The drought path calls no AI model and uses only free data, so it adds nothing to running costs; where an IPC API key is unavailable it falls back to the Phase 3+ figures Fred already collects, which is what makes it work for the FEWS NET countries where drought matters most.
- **The resolution machine now has a history, base rates, and a scorecard.** Its fifth and final phase replays the machine over the past — cyclones from 2000, floods from 2010, droughts from 2017 — using the *same* detection, ladder and rules as a live run, with nothing but a label distinguishing the two. That sameness is the point: base rates drawn from a history the machine did not actually produce would describe a different machine, and a rule change could then quietly move today's grades without moving the history they are compared against. Because every replayed month is long past the 60-day freeze, the replay can only fill gaps — a month already graded keeps its answer and the attempt is logged instead. The replay is resumable, since it runs for hours and re-grading settled months would bury the genuine revision log under thousands of no-op entries. From that history come two things forecasters use: **how often a hazard occurs** in a given country and calendar month, counted only over years the machine genuinely examined (treating an unexamined month as a quiet one would manufacture a low rate out of a data gap, and country-months with under three years of evidence are not published at all); and **how bad it is when it does** — the spread of graded figures since 2015, carrying the mix of sources behind it year by year, including what share came from displacement counts, because a spread built from displacement figures is a spread of *floors* and the percentiles alone cannot say so. Flood detection additionally gets an **independent check**: the Dartmouth Flood Observatory's hand-curated archive reaches back to 1985, so the machine compares how often it finds floods against how often that archive found them in the years *before* GDACS became reliable, and lists countries where it appears to be missing events. That archive is calibration only — it never triggers a hazard and never supplies a figure. Finally, a **one-page scorecard** covers the last twelve settled months: the share graded per hazard against both the 80% goal and the IFRC-only baseline it replaces, flagged rows by reason, where the answers came from, and twenty graded zeros and twenty graded figures with their evidence, drawn with a fixed seed so a reviewer can regenerate the identical page. It divides by every month the machine *looked at* rather than by the ones it answered, reports a hazard with nothing examined as "not assessed" instead of 0%, and where the machine falls short it states the shortfall and says plainly that the gap is to be reported rather than closed by loosening a threshold.

### Data feeds and coverage

- **Food-crisis questions now cover every country with real IPC data, and country coverage can no longer silently shrink.** A July 2026 review found two related gaps. First, countries whose food-security data comes only from the IPC's own API (rather than FEWS NET) could never receive a food-crisis question, because the eligibility list those questions depend on was produced during data ingestion and never made it to where questions are generated — the question generator now also checks the database directly, so any country with recent Phase 3+ data is eligible. Second, a data-refresh run with a short look-back window used to overwrite the list of FEWS NET-monitored countries with only the countries seen in that window (48 shrank to 27 in one run), which would have quietly dropped food-crisis coverage; the lists are now only ever added to, never shrunk, and the run summary raises a warning if a shrink is ever detected again.

## System at a Glance

Fred (also referred to as Pythia in the codebase) is an end-to-end humanitarian forecasting system. It takes raw event data (conflict, disasters, displacement) from three primary sources — ACLED, IDMC, and IFRC GO — supplements that data with structured feeds from humanitarian monitoring organizations (ACAPS, IPC, ReliefWeb, HDX Signals), climate forecast services (NOAA/NMME, IRI/CPC ENSO forecasts, seasonal TC outlooks from TSR/NOAA CPC/BoM/Météo-France La Réunion), conflict forecast models (VIEWS, conflictforecast.org, ACLED CAST), and expert assessments (ICG CrisisWatch), and produces probabilistic forecasts for a set of standardized questions over a 1–6 month horizon. The system is designed for auditability: each run writes a canonical DuckDB database artifact that records inputs, intermediate judgments, model calls, and final outputs.

A key design tension in forecasting is balancing base rates (what usually happens) with out-of-pattern events (what can happen when the world changes). In Fred, this tension is handled explicitly through Horizon Scanner triage, Regime Change scoring, and adversarial evidence checks that stress-test any out-of-pattern hypothesis before it reaches a forecast.

## 1. Purpose, scope, and forecasting philosophy

Fred is built to support recurring humanitarian decision-making under uncertainty. It converts disparate, noisy real-world observations into probabilistic statements about near-term outcomes. Those statements are not point forecasts. Instead, the system produces distributions over outcome bins, allowing users to reason about risk, tails, and uncertainty rather than a single best guess.

The system assumes that base rates matter: for many humanitarian metrics, the best starting point is what typically happens in a country given its recent history and seasonality. However, base rates are not sufficient. Humanitarian outcomes often exhibit structural breaks driven by conflict escalation, sudden displacement, extreme weather, policy shifts, or compound shocks. A central design goal is therefore to detect and communicate when "business as usual" may not apply, and to help forecasters allocate probability mass to out-of-pattern outcomes when warranted.

Fred is designed as an auditable pipeline. Each stage writes its outputs into a single DuckDB database artifact, and the artifact is treated as the canonical record for that run. This enables reproducibility (rerunning with the same artifact) and forensic debugging (tracing why a forecast moved).

## 2. Core objects and terminology

To understand Fred, it helps to start with the system's core objects: facts, hazards, questions, evidence, and forecasts.

A **fact** is a normalized observation derived from an upstream source (for example, monthly conflict events or fatalities from ACLED, disaster impacts from IFRC GO, or displacement figures from IDMC). Facts are stored with metadata describing provenance and, where possible, a notion of "as-of" time. Facts are later "resolved" into ground truth used for scoring.

A **hazard** is a high-level class of humanitarian risk that Fred tracks consistently across countries. The four active pipeline hazards are: ACE (armed conflict events and impacts), DR (drought), FL (flood), and TC (tropical cyclone). Several other hazard codes remain in the configuration but are fully silenced — DI (displacement inflows), CU (civil unrest), HW (heat wave), and the retired ACO (an older armed-conflict code superseded by ACE) — meaning they are blocked at the hazard catalogue level and never enter RC assessment, triage, grounding, or question generation. A couple of further codes (EC, PHE) are defined in the configuration but have never been switched on. They were removed because no reliable resolution source exists for them, making forecasts unscoreable. The pipeline processes exactly four hazards per country (minus seasonal screen-outs for TC). These codes provide a stable vocabulary that connects HS triage, evidence gathering, question generation, and forecasting.

A **question** is the unit that gets forecast. A question typically represents a country–hazard–metric combination, evaluated across the next six months. The system forecasts each month's outcome using a discrete probability distribution over bins that correspond to meaningful ranges for the metric.

**Structured data** refers to the authoritative humanitarian, climate, and conflict-forecast datasets pulled from specialist APIs (ReliefWeb, ACAPS, IPC, ACLED political events, NMME/NOAA, IRI/CPC ENSO, seasonal TC forecasts, VIEWS, conflictforecast.org, ACLED CAST, HDX Signals, ICG CrisisWatch). Unlike web-search-derived evidence packs, structured data is deterministic, reproducible, and sourced from organizations with formal data collection methodologies. Structured data is stored in the database and automatically formatted for injection into pipeline prompts.

An **evidence pack** is a grounded research bundle generated via web search, used primarily by the Horizon Scanner for triage and Regime Change assessment. Evidence packs include structural context (slow-changing background) and recent signals (time-bounded observations), each anchored to sources.

A **forecast** is represented as an SPD (a discrete probability distribution) per month. The system often runs multiple models and aggregates them into an ensemble forecast. The ensemble is treated as the system's primary forecast output for dashboarding and evaluation.

## 3. Resolver: data ingestion, normalization, and base-rate foundation

Resolver is the system's quantitative backbone. It ingests data from three active connectors and transforms them into monthly facts suitable for (a) base-rate estimation and (b) later scoring. Resolver is not a forecasting model. It is a data pipeline with strong opinions about consistency and auditability.

Resolver connectors pull from external providers. In a February 2026 refactoring, seven defunct or disused connectors (including EM-DAT, DTM, IPC, ReliefWeb, UNHCR, WFP, and WHO) were removed and the system was consolidated behind a formal connector protocol. Six active connectors now feed the Resolver: ACLED (conflict event and fatality records), IDMC (internal displacement flows via the Helix API), IFRC Montandon (natural-hazard people-affected data via the IFRC GO API, replacing the former EM-DAT connector), GDACS (disaster population exposure for floods, droughts, and tropical cyclones), FEWS NET IPC (food security Phase 3+ population estimates for 48 monitored countries), and IPC API (food security Phase 3+ population estimates for non-FEWS NET countries such as Afghanistan, Pakistan, and Guatemala, via api.ipcinfo.org). IFRC GO provides structured impact data across multiple metrics (affected, fatalities, injured, displaced, missing) and maps disaster types to hazard codes automatically using IFRC's own disaster-type classification. GDACS writes two metrics per country-month-hazard: `in_need` (population exposed, used for PA-based forecasts) and `event_occurrence` (a binary 1/0 indicator based on alert level, where Orange or Red alerts count as events and Green alerts do not). The `event_occurrence` metric supports binary forecast questions that ask whether a significant disaster event will occur, complementing the SPD-based forecasts that estimate impact magnitude. FEWS NET IPC writes `phase3plus_in_need` (current situation, used for resolution) and `phase3plus_projection` (most likely scenario, used as context in forecaster prompts).

The ingestion process writes fact rows into tables that track what changed (deltas) and what is considered resolved ground truth. In practice, this means there is a "facts_deltas" table that accumulates incremental connector writes, and a "facts_resolved" table used for evaluation, where each country–hazard–month has an authoritative value once it becomes stable. Two legacy tables (emdat_pa and acled_monthly_fatalities) are also consulted as fallbacks when more recent sources lack data for a given month.

Why this architecture matters for forecasting: the deltas table is the freshest view of what the system has most recently ingested; the resolved table provides a stable reference for scoring and calibration. This split helps prevent a common forecasting pitfall: scoring a forecast against data that later gets revised without keeping a record of what the system 'knew' at the time of forecasting. When the system resolves ground truth for scoring, it uses a four-table priority cascade: facts_resolved (highest priority), then facts_deltas, then emdat_pa (for people-affected metrics only), then acled_monthly_fatalities (for fatality metrics only). The cascade short-circuits: once any table returns a value for a country–hazard–month, lower-priority tables are not queried.

Operationally, Resolver is usually run through a GitHub Actions workflow (often called an initial backfill). This workflow can rebuild the database from scratch or incrementally backfill a set number of months. It also supports policies for how to treat '0 rows written' situations, which are important because external sources can occasionally return empty responses due to outages, rate limits, or schema changes. Two important safeguards were added in February 2026: a calendar cutoff prevents resolution of the current (incomplete) month — only fully completed calendar months are eligible for resolution — and a data-driven cutoff prevents resolution of months beyond the latest data actually present in any source table. A stale-resolution purge runs at the start of each resolution pass, deleting any resolution rows that were incorrectly written for future or partial months in earlier pipeline runs, along with their associated scores, and reverting affected questions to active status so they can be re-resolved correctly.

A key limitation — and one that users must internalize — is that these data sources are imperfect proxies for humanitarian impact. They reflect reporting incentives, access constraints, and definitional choices. Fred does not pretend this disappears. Instead, it tries to surface uncertainty explicitly through data-quality notes, model uncertainty, and regime-change flags.

### The resolution machine: closing the people-affected scoring gap

Because the IFRC publishes a matching field report for only a few percent of country-months, most people-affected forecasts were never graded. A dedicated resolution machine was built to change that, with a target of grading at least 80% of country-month-hazard combinations to a number (including zero) rather than "no data". It works in two layers: first *did anything happen?*, then *how many people did it affect?* All three hazards it covers — cyclones, floods and droughts — are built, so is the historical backfill that turns those grades into base rates, and so is the last step that puts those base rates in front of the forecasting models.

**Layer one: did anything happen?** For cyclones, the machine asks two independent questions per country-month — did any tropical-storm-strength track in the official global storm archive pass within 200 km of the country's territory, and did ReliefWeb's humanitarian reporting mention a cyclone for that country in that window? For floods, the first question is instead whether GDACS raised a flood alert of orange or red for that country. Two clean "no" answers produce a confident zero, stored with the complete evidence of absence. A hazard detection (or reporting without a detection, as happens with remnant storm systems) instead sends the month to layer two.

**Layer two: how many people?** The machine walks a fixed, published ladder of reporting sources and takes the figure from the highest rung that has one: EM-DAT, then figures stated in ReliefWeb documents, then IFRC field reports, then IDMC displacement counts. A lower rung that disagrees is never allowed to overturn a higher one — disagreement raises a flag for human review, it does not change the number. Displacement figures are published as a *lower bound*, since displaced people are a subset of affected people. Every figure is checked against what GDACS estimates was exposed to the hazard and against the country's population; a figure that breaks either ceiling is kept and flagged rather than quietly rewritten. GDACS's own estimate is used only as that ceiling and is never published as an answer, because it is a model of who was *exposed*, not a count of who was *affected*.

**Drought is different, and takes a different route.** Nothing makes landfall and no alert turns orange; there is no day on which a drought "happens". What exists instead is the IPC/CH food-security analysis cycle, so drought skips the ladder altogether. The machine takes the *increase* in the population classified at IPC Phase 3 or above between one analysis and the previous one, floored at zero — the number of people who newly fell into crisis-level food insecurity. Because IPC states how many people are in Phase 3+ but never says *why* — the driver is discussed in narrative reports, not in any data field — that increase is only published as drought impact where an independent agricultural-drought indicator agrees the country was in drought. Without that check, conflict- and price-driven hunger would be filed as drought, which would corrupt the ground truth the forecasts are graded against. The same two signals decide a drought zero: no drought indicator and no Phase 3+ deterioration together justify a confident zero, and an indicator that could not be *read* suppresses the zero rather than permitting it.

An IPC analysis is valid across several months but states one figure, so the machine cannot invent a monthly breakdown. It publishes the same increase for every month the analysis covers — the people who fell into crisis are still in crisis for the analysis's duration — and each grade says on its face that these are standing totals which must not be added up across months. Two cases are deliberately refused rather than guessed: a country with a current analysis but no earlier one to compare against is graded "no data", because that single figure is a *standing total*, not the month's newly affected, and publishing it would overstate by the entire pre-existing caseload; and a month where drought conditions are indicated but IPC has published nothing by the freeze deadline is graded "no data" and flagged, which is the honest answer.

**Running it over history, and checking whether it worked.** Grading only the months ahead would say nothing about how good the machine is, and would leave the forecasters without history to anchor on. So the same machine — the same detection, the same ladder, the same rules, with no separate historical code path — is replayed month by month over the past: cyclones from 2000, floods from 2010, droughts from 2017. Each hazard's start year is set by when its detector's record actually begins rather than by preference; running earlier than that would produce empty months, not extra evidence. Because every one of those months is long past the 60-day freeze, the replay can only *fill gaps*: any month already graded keeps its answer, and the attempt is logged rather than applied. The replay is resumable, since it runs for hours and a re-run that re-graded settled months would bury the genuine revision log under thousands of no-op entries.

That history produces two things forecasters can use. **How often does this happen?** — for each country, hazard and calendar month, the share of replayed years in which the hazard actually occurred. The denominator counts only years the machine genuinely assessed, never years it simply has no record of, because treating an unexamined month as a quiet one would manufacture a reassuringly low rate out of a data gap. Country-months with fewer than three years of evidence are not published at all: one observed November is not a base rate, and a rate of "100%" from a single year reads as certainty. **And how bad is it when it does?** — the spread of graded figures per country since 2015, reported as a set of percentiles. Each of those carries the mix of sources behind it, year by year, including what share came from displacement counts. That last number matters: a spread built mostly from displacement figures is a spread of *floors*, not of estimates, and the percentiles alone cannot tell you that.

**An independent check on flood detection.** The machine detects floods with GDACS, which only becomes reliable around 2010 — so its own flood history cannot tell us whether it is missing floods. The Dartmouth Flood Observatory has hand-curated a flood archive back to 1985, so the machine compares how often it finds floods in a country against how often that independent archive found them in the years *before* GDACS. Countries where the archive records far more floods than the machine sees are listed for a human to investigate. This comparison is calibration only: the archive never triggers a hazard and never supplies a figure, and the windows deliberately do not overlap, because checking the machine against years it already graded from would confirm nothing.

**And an honest scorecard.** A one-page report covers the last twelve fully settled months: the share of country-month-hazard combinations graded per hazard, against both the 80% goal and the IFRC-only baseline it replaces — recomputed from the machine's own data rather than merely quoted. Three choices keep it from flattering itself. It divides by every combination the machine *looked at*, not by the ones it managed to answer, so months it examined and could not grade count against it. A hazard with no examined months at all is reported as "not assessed" rather than as 0%, because an absence of evidence is not a failure. And the twenty graded zeros and twenty graded figures it shows as worked examples, complete with their evidence, are drawn using a fixed seed, so a reviewer who checks a row can regenerate the identical page. Where the machine falls short of the target, the report states the shortfall per hazard and says plainly that the gap is to be reported, not closed by loosening a threshold until the number looks better.

**Telling the forecasters what they will be graded against.** Base rates sitting in a table change nothing, so the last step puts them in front of the models. Every people-affected question about a cyclone, flood or drought now carries a short block in its forecasting prompt: how often the hazard has occurred in that country in each of the six months being forecast, how large it has been when it did occur, where those figures came from, and — in two plain sentences — the rule that will decide the answer. A forecaster that does not know the grading rule is guessing at the target as well as at the world; one that knows a quiet month is graded a confident zero rather than left ungraded will allocate probability differently, and correctly.

That description is written by the machine from its own rulebook every time a prompt is built, rather than typed into the prompt text. The 200 km buffer, the storm-strength threshold, the orange alert level, the order of the reporting ladder, the 60-day freeze: each is read from the rulebook at that moment, so changing a threshold changes what the models are told on the next run, with nothing to keep in step by hand. A prompt still describing last quarter's rules would be confidently wrong, which is worse than one describing no rules at all.

Four things about the block are deliberate. It is shown **only** for people-affected questions on the three hazards the machine grades — food-crisis questions ask about the number of people *already* in crisis, while the machine's drought figure is the monthly *increase* in that number, and putting one where the other belongs would mislead by the entire pre-existing caseload. A country with too few graded events says how many it has rather than showing a spread, because five percentiles read as a distribution however they are labelled, and anchoring on the spread of two events is worse than anchoring on none. A country the machine has **never examined** gets no block at all, rather than one reading "no events on record" — that would state as fact something nobody ever checked. And the whole block is kept to around 200 words, because prompt space spent here is prompt space taken from current evidence; a rate that is small but real is written "<1%" rather than rounded to zero, and drought carries an explicit warning that its record is only about eight years deep and patchy by country.

Four guarantees run through the whole machine. Every grade carries its provenance — what was queried, what was found, when, and which rule fired. Grades freeze 60 days after month-end and are never rewritten; later revisions are logged, not applied, and grades written before the deadline are marked provisional. A zero is refused whenever the detection source hasn't demonstrably caught up with the month, so an ingestion gap can never be mistaken for a quiet month. And a source that could not be reached is always recorded as unread rather than empty — the machine will wait, or say "no data", but it will never turn its own outage into a zero. Every threshold in every one of these rules — the 200 km buffer, the orange alert level, the tenfold disagreement test, the 60-day freeze, the ladder's order — lives in one reviewable rulebook file that can be changed without touching code.

## 4. Structured data connectors: authoritative humanitarian and forecast feeds

A major architectural shift in the March 2026 version replaced the former "Research LLM" stage with direct structured data connectors. Previously, the system used an LLM to generate research briefs by conducting web searches, synthesizing results, and writing a brief. This approach was effective but introduced variability — the same question could produce different evidence depending on which web results the LLM encountered. The new architecture pulls structured data directly from authoritative humanitarian, climate, and conflict-forecast APIs, stores it in the database, and injects it into prompts as pre-formatted text blocks. This makes the evidence pipeline deterministic, reproducible, and anchored to organizations with formal data collection methodologies.

Fred now maintains seventeen structured data feeds, organized into five categories: humanitarian monitoring, food security, climate and seasonal forecasts, conflict forecasts, and automated crisis monitoring. These feeds are used across the entire pipeline — Horizon Scanner RC assessment, HS triage, and the forecaster — though not every feed appears in every prompt. The table at the end of this section summarizes which feeds are injected where.

### Humanitarian monitoring feeds

**ReliefWeb situation reports.** ReliefWeb, operated by the UN Office for the Coordination of Humanitarian Affairs (OCHA), publishes humanitarian situation reports, assessments, and updates from agencies operating in the field. Fred fetches recent reports for each country (looking back 45 days, up to 15 reports), extracts key metadata (title, source organizations, disaster types, themes, publication date), and stores them in the database. These reports provide on-the-ground operational context that complements quantitative data — for example, a ReliefWeb flash update about sudden flooding or a situation report about a cholera outbreak. ReliefWeb data is used across all pipeline stages and all hazard types.

**ACAPS INFORM Severity Index.** The INFORM Severity Index is a composite score maintained by ACAPS that measures the overall severity of humanitarian crises. It combines indicators of crisis impact, conditions of affected people, and crisis complexity into a single score with trend data (improving, stable, deteriorating). Fred fetches the latest severity scores and trends for each country. This provides a standardized, cross-comparable measure of crisis severity that helps calibrate expectations about where a country sits on the spectrum from stable to acute crisis.

**ACAPS Risk Radar.** Risk Radar is ACAPS's forward-looking risk assessment tool. It identifies countries and crises where humanitarian conditions are expected to deteriorate in the near term, along with specific triggers (the events or conditions most likely to cause deterioration). Because Risk Radar is explicitly forward-looking and trigger-oriented, it is particularly valuable for forecasting — it provides expert assessments of what could go wrong, rather than just what has already happened.

**ACAPS Daily Monitoring.** ACAPS analysts produce daily curated updates tracking significant developments across active crises. Fred fetches recent monitoring entries for each country, providing a stream of analyst-vetted situational awareness. These updates fill the gap between the relatively slow-moving Resolver facts (which are monthly aggregates) and the real-time developments that can affect near-term forecasts.

**ACAPS Humanitarian Access.** Humanitarian access scores measure the degree to which aid organizations can reach affected populations. Access constraints (insecurity, bureaucratic restrictions, physical barriers) are a critical contextual factor for humanitarian outcomes — a country with deteriorating access is likely to see worse outcomes even if the underlying hazard conditions are unchanged. Fred fetches access constraint scores and injects them into HS triage prompts (but not into the forecaster SPD prompt).

**ACLED Political Events.** In addition to the monthly aggregate conflict data already ingested through the Resolver, the system pulls event-level political data from ACLED. This includes specific incidents such as strategic developments, protests, riots, and political violence events. Unlike the Resolver's monthly summaries (which provide base-rate counts), political events provide narrative detail about what is actually happening — for example, a protest movement gaining momentum, a military coup, or a ceasefire announcement. Political events are used selectively: they are injected into prompts only for armed conflict (ACE) hazards, where event-level context is most relevant. (The code also references displacement (DI), but DI is blocked from the active pipeline.)

### Food security feeds

**FEWS NET IPC Phase 3+ Population Estimates.** The Famine Early Warning Systems Network (FEWS NET), operated by USAID, publishes IPC-compatible food security phase classifications for 48 monitored countries. Fred fetches population estimates from the FEWS NET Data Warehouse, focusing on two scenarios: Current Situation (used for forecast resolution and scoring) and Most Likely (used as forward-looking context in prompts). For each country and analysis period, the system stores the population classified at IPC Phase 3 or above ("Crisis or worse"), which is the primary metric for the PHASE3PLUS_IN_NEED forecast metric. FEWS NET data is used for drought (DR) hazard questions: in FEWS NET-monitored countries, DR questions use PHASE3PLUS_IN_NEED as their forecast metric rather than people affected (PA), because FEWS NET Phase 3+ provides more precise and operationally relevant ground truth for food-security-driven crises. The system maintains lists of both FEWS NET-monitored and IPC API-monitored country ISO3 codes, and DR/PA questions are blocked for countries not covered by either source to prevent unresolvable forecasts.

**IPC API Phase 3+ Population Estimates.** The IPC API connector fetches Phase 3+ population data from api.ipcinfo.org for countries not covered by FEWS NET. It requires an IPC access key and explicitly excludes FEWS NET countries (FEWS NET always takes priority). This extends food security ground truth beyond the 48 FEWS NET-monitored countries to additional food-insecure countries. The unified food security loader tries FEWS NET first and falls back to the IPC API, so DR questions can now be generated and resolved for any country with food security data from either source. A legacy `ipc_phases` table exists in the codebase from an earlier connector but is no longer populated or used.

### Climate and seasonal forecast feeds

**NMME Seasonal Climate Forecasts.** The North American Multi-Model Ensemble (NMME) provides seasonal temperature and precipitation anomaly forecasts from the NOAA Climate Prediction Center. Fred downloads the ensemble mean forecasts, computes country-level area-weighted averages, and stores the results in the database. For each country, the system provides anomalies for the next seven months, expressed as standard deviations from climatology, along with derived tercile categories (above normal, below normal, near normal). These forecasts are used for climate-sensitive hazards — drought, flood, heatwave, and tropical cyclone — giving the pipeline concrete quantitative signals about expected climate conditions rather than relying solely on qualitative web-search evidence. The data is refreshed monthly via a scheduled pipeline, typically around the 10th of each month when new NMME data becomes available.

**ENSO State and Forecast (IRI/CPC).** The ENSO module scrapes the International Research Institute (IRI) and Climate Prediction Center (CPC) ENSO Quick Look page to retrieve comprehensive ENSO conditions. The scraped data includes: the current ENSO state classification (La Niña, Neutral, or El Niño), the latest Niño 3.4 SST anomaly value, a 9-season probabilistic forecast table showing the probability of La Niña, Neutral, and El Niño for each upcoming 3-month season (e.g., MAM, JJA, SON), multi-model plume averages broken down by model type (dynamical models, statistical models, and all models combined), Indian Ocean Dipole (IOD) state and the Dipole Mode Index (DMI) value, and the CPC's narrative summary. The data is cached for seven days before being re-fetched, and is available both as structured fields (for charts and checks) and as a ready-made block of prompt text. ENSO context is injected into RC and triage prompts for climate-sensitive hazards (DR, FL, TC), because ENSO phase is a major driver of seasonal precipitation patterns, tropical cyclone activity, and drought risk globally. For example, El Niño conditions typically suppress Atlantic hurricane activity while enhancing Pacific activity, and increase drought risk in parts of Southeast Asia and Australia — information that the pipeline previously had to discover anew through web searches on every run.

**Seasonal Tropical Cyclone Forecasts (TSR, NOAA CPC, BoM, Météo-France La Réunion, IMD/NIO climatology).** This module aggregates basin-level seasonal tropical cyclone forecasts from independent authoritative sources, covering eight named ocean basins:

- **Tropical Storm Risk (TSR)**: TSR publishes detailed PDF forecast documents for the Atlantic (ATL) and Northwest Pacific (NWP) basins. The extractor uses `pdfplumber` with regex-based parsing to discover and download TSR PDFs by their predictable URL naming convention (e.g., `TSRATLForecastApr2026.pdf`), then extracts named storm counts, hurricane/typhoon counts, intense hurricane/typhoon counts, Accumulated Cyclone Energy (ACE) index predictions, comparisons against 30-year and 10-year norms, tercile probability distributions (above/near/below normal), and ENSO context notes. TSR provides the most granular quantitative seasonal forecasts available.

- **NOAA Climate Prediction Center (CPC)**: NOAA publishes seasonal hurricane outlook press releases for the Atlantic (with an initial May forecast and an August update), Eastern North Pacific (ENP), and Central Pacific (CP) basins. The scraper extracts named storm, hurricane, and major hurricane ranges (e.g., "14–21 named storms"), above/near/below-normal probability assessments, and key explanatory factors. A single NOAA press release sometimes covers multiple basins, and the scraper handles cross-basin references by parsing the document for each relevant basin.

- **Australian Bureau of Meteorology (BoM)**: BoM publishes seasonal TC outlooks for the Australian region (AUS) and South Pacific (SP). The scraper extracts the probability of above-average activity, categorical outlooks (above/below/near average), subregional breakdowns (e.g., Western, Northern, and Eastern Australia), and notes on severe TC likelihood. BoM outlooks use a different structure from TSR and NOAA — they emphasize probability of above-average rather than specific count ranges — and the scraper normalizes these into the same output format.

- **Météo-France La Réunion (RSMC)**: the official Regional Specialised Meteorological Centre for the South-West Indian Ocean (SWI) publishes an annual seasonal cyclone activity outlook (issued each October/November for the November–April season) as a French-language article. The scraper extracts the expected number of named systems, how many are expected to reach tropical cyclone strength, probability assessments where given, and El Niño/Indian Ocean Dipole commentary. This closes the previous coverage gap for Madagascar, Mozambique, Malawi and the other SWI countries. Outside the season the most recent edition is served, clearly labeled with its season.

- **North Indian Ocean climatology (IMD/RSMC New Delhi)**: India's meteorological agency publishes no seasonal cyclone count outlook, so the NIO basin (Bangladesh, Myanmar, India, Sri Lanka, Pakistan, Oman, Yemen, Somalia, Iran's Makran coast) receives a climatology block instead: average storm counts, the strongly two-peaked seasonality (April–June and October–December), and which coasts each sub-basin threatens. When RSMC New Delhi's weekly two-week cyclogenesis outlook is fresh, its Bay of Bengal / Arabian Sea probabilities are attached as well. The block states explicitly that it is climatological context, not a seasonal count forecast.

All sources are deduplicated by (source, basin, forecast_type), keeping the most recent forecast when multiple versions exist. The results are unified into a JSON cache and an optional `prompt_context.txt` file. At prompt time, the system maps each country to its relevant ocean basin(s) using a comprehensive country-to-basin lookup table (for example, the Philippines maps to the Northwest Pacific, Madagascar maps to the Southwest Indian Ocean), and assembles a text block containing every seasonal forecast available for those basins. Landlocked and non-cyclone-exposed countries simply receive nothing. A staleness warning is included if the cached forecasts are more than 120 days old. Seasonal TC context is injected into TC-specific RC and triage prompts, providing the pipeline with expert consensus on basin-level activity expectations — information that directly calibrates whether the upcoming season is expected to be above, near, or below average for a given region.

### Conflict forecast and assessment feeds

**VIEWS (Uppsala/PRIO).** VIEWS is a machine-learning-based conflict forecasting system developed at Uppsala University and the Peace Research Institute Oslo. It provides country-month predictions of state-based conflict fatalities and the probability of at least 25 battle-related deaths at 1–6 month lead times. VIEWS is generally stronger at capturing trends and baseline levels of conflict, though weaker at predicting sudden onset. Fred stores VIEWS predictions in the database and includes staleness warnings when the data is more than 45 days old.

**conflictforecast.org (Mueller/Rauh).** This project provides news-based armed conflict risk scores derived from media coverage patterns. It offers risk scores at 3-month and 12-month horizons, plus a violence intensity outlook at 3 months. Because it is driven by news signals rather than historical conflict patterns, conflictforecast.org is generally better than VIEWS at detecting shifts and escalation signals. Where the two quantitative sources disagree, the LLM is instructed to note the disagreement and reason about why.

**ACLED CAST (Conflict Alert System Tool).** ACLED CAST provides event-count forecasts disaggregated by event type: total events, battles, explosions/remote violence (ERV), and violence against civilians (VAC). CAST uses an OAuth2-authenticated API and returns admin1-level forecasts that the connector aggregates to country level. Four distinct metrics are stored: `cast_total_events`, `cast_battles_events`, `cast_erv_events`, and `cast_vac_events`, each covering a 6-month forecast horizon. CAST differs from VIEWS and conflictforecast.org in two important ways. First, it forecasts event counts rather than fatalities, providing a complementary signal — a country could see rising event counts (more frequent clashes) without a proportional rise in fatalities, or vice versa. Second, the event-type breakdown (battles vs. ERV vs. VAC) reveals shifts in the character of violence that aggregate counts would mask. For example, a shift from battles to violence against civilians may indicate a change in conflict dynamics even if total event counts remain stable. CAST forecasts are rendered alongside VIEWS and conflictforecast.org in a unified conflict forecast block, with a note explaining that CAST measures event counts rather than fatalities. Country name aliases are used for ISO3 resolution (for example, mapping "Ivory Coast" to CIV, or "Congo DRC" to COD).

**ICG CrisisWatch (International Crisis Group).** CrisisWatch is ICG's monthly conflict monitoring bulletin. The system fetches per-country directional assessments (Deteriorated, Improved, Unchanged) and the monthly "On the Horizon" feature, which highlights roughly three conflict risks and one resolution opportunity expected in the next three to six months. ICG is highly selective about what it flags, so countries appearing in "On the Horizon" receive a prominent note in their RC assessment. CrisisWatch data is sourced primarily from a local JSON file produced by a scraper that runs monthly in the cloud. Because the ICG website blocks automated fetches from cloud servers, the scraper reads the Internet Archive's copy of the CrisisWatch page instead: it requests a fresh snapshot, verifies the snapshot is genuine (not a blocked page), parses it with BeautifulSoup, and commits structured JSON to the repository — but only when the parsed edition is genuinely newer than what is already stored. A local browser-based path is kept for manual refreshes. A Gemini grounding fallback is only attempted when the JSON file is missing or empty. Data is persisted in the `crisiswatch_entries` DuckDB table (keyed by country, year, and month) and is fetched once at the start of each Horizon Scanner run, then passed through to all country workers for consistency. A staleness warning is logged if the JSON file is more than 45 days old, but the data is still used.

All conflict forecast feeds are used exclusively for armed conflict (ACE) hazards. VIEWS, conflictforecast.org, and ACLED CAST predictions are stored in the database and injected alongside the ACLED retrospective base rates as structured quantitative anchors. The prompt rendering includes staleness warnings for each source when data is older than 45 days, and explicitly notes where sources agree or disagree on trend direction. ICG CrisisWatch is injected into ACE RC and ACE triage prompts.

### Automated crisis monitoring

**HDX Signals (OCHA).** HDX Signals is an automated crisis monitoring system operated by OCHA's Centre for Humanitarian Data. It continuously monitors a set of global indicators and generates alerts when anomalous or noteworthy conditions are detected. The connector downloads the `hdx_signals.csv` dataset from the HDX CKAN API and caches it locally.

Each HDX Signals indicator type is mapped to one or more Fred hazard codes:
- `acled_conflict` → ACE (armed conflict)
- `idmc_displacement_conflict` → ACE
- `idmc_displacement_disaster` → FL, TC, DR (disaster-driven displacement)
- `ipc_food_insecurity` → DR (food security as a drought proxy)
- `jrc_agricultural_hotspots` → DR (agricultural stress)
- `wfp_market_monitor` → DR (market disruption as a drought indicator)
- `acaps_inform_severity` → all hazard types

Alerts are filtered by country (ISO3), hazard relevance, and recency (default 180 days). The formatted output for prompt injection includes for each alert: the indicator name, alert level, summary text, date, and source URL. The connector includes a disclosure note that HDX Signals alerts are suppressed for 6 months after the last alert for a given indicator-country pair, so the absence of recent alerts does not necessarily mean the absence of concerning conditions. HDX Signals is injected into both RC and triage prompts for all hazard types, providing a broad automated screening layer that complements the more targeted individual data sources.

**GDELT conflict indicators.** GDELT (the Global Database of Events, Language, and Tone) continuously codes news reports worldwide into structured event records using the CAMEO taxonomy. Fred's GDELT connector downloads the free daily event exports, classifies events by CAMEO tier (direct violence, escalatory posture, political deterioration), and stores per-country daily aggregates — total event count, material/verbal conflict counts, Goldstein cooperation-conflict scores, and average tone of conflict reporting. At prompt time, the connector computes rolling 7-, 30-, and 60-day windows and reports the trend direction, so the forecaster can see whether the recent media picture shows rising, falling, or flat conflict temperature. GDELT is used only for armed conflict (ACE) questions and is injected into the ACE RC, ACE triage, and ACE forecaster SPD prompts. Because GDELT is media-derived, the prompt block includes an explicit caveat that counts reflect reporting activity and tone, not verified ground-truth fatalities — those come from ACLED.

## 5. Web research evidence packs: grounded qualitative signals

Evidence packs provide qualitative context that does not fit neatly into the structured datasets. While structured data connectors (Section 4) handle the bulk of evidence for the forecaster, evidence packs remain the primary evidence mechanism for the Horizon Scanner's triage and Regime Change assessment.

An evidence pack has two primary components. Structural context provides brief background drivers that change slowly (governance, exposure, long-running conflict dynamics). Recent signals provide a set of time-bounded observations intended to affect the 1–6 month horizon. Recent signals should be testable: they should point to observable developments rather than general commentary.

Fred's evidence packs are designed to be grounded: they carry explicit source URLs and are generated within a recency window (30–90 days depending on hazard and purpose). This is essential for credibility. When evidence is thin or contradictory, the system is instructed to say so rather than fabricate certainty.

The Horizon Scanner now generates separate grounding calls per hazard, and the grounding calls are different for RC and triage (see Section 6 for details). The RC grounding uses signal categories tuned for novelty detection — TRIGGER, DAMPENER, BASELINE — while the triage grounding uses categories tuned for the operational picture — SITUATION, RESPONSE, FORECAST, VULNERABILITY. This separation ensures that the LLM's web search is calibrated to the specific question being asked (is the pattern changing? vs. how bad is it?) rather than trying to answer both with a single query.

The former question-level web research pipeline — which generated per-question evidence packs for the forecaster using LLM-directed web searches — has been fully deprecated and bypassed. Evidence packs remain active for the Horizon Scanner's grounding calls, but the forecaster receives all its evidence through structured data connectors (Section 4) and Horizon Scanner outputs, which is more deterministic and reproducible.

## 6. Horizon Scanner (HS): per-hazard risk screening with dedicated grounding

Horizon Scanner is the system's front-end risk screening stage. Its job is not to forecast numbers. Instead, it triages which country–hazard combinations merit deeper attention and provides structured context for downstream forecasting.

HS is typically run on a schedule (for example, monthly) and writes into the canonical DuckDB. Two tables are important for understanding HS outputs. The hs_country_reports table stores the evidence pack used for a country (including sources and markdown renderings). The hs_triage table stores one row per country–hazard, including the triage score and other structured fields.

### Per-hazard pipeline architecture

The HS pipeline has been restructured in this version into a fully per-hazard architecture. Rather than producing a single assessment per country that tries to evaluate all hazards simultaneously, the pipeline now runs dedicated RC and triage assessments for each individual hazard. For a country exposed to four hazard types (ACE, DR, FL, TC), the pipeline produces four separate RC assessments and four separate triage assessments, each with its own grounding call, prompt, and LLM invocation.

The pipeline runs in the following order for each country:

1. **Per-hazard RC grounding** — For each hazard, a dedicated web search grounding call is made using hazard-specific search queries with hazard-specific search labels (e.g., "armed conflict violence displacement humanitarian situation" for ACE, "flooding displacement humanitarian impact" for FL). The primary search backend is the Brave Search API, with OpenAI and Gemini as fallbacks. The RC grounding queries are designed to detect signals of structural change — new conflict dynamics, unusual climate patterns, policy shifts — rather than to describe the current situation. Each query specifies signal categories (TRIGGER, DAMPENER, BASELINE), a hazard-appropriate recency window (30 days for ACE and FL; 60 days for DR and TC), and a source-priority list that favors wire services and specialist sources for novelty detection. These grounding calls run in parallel across hazards using a thread pool.

2. **Per-hazard RC assessment** — For each hazard, the RC LLM is invoked with the grounding results plus all relevant structured data for that hazard. The RC prompt is hazard-specific (see Section 7 for details). RC runs a single pass by default, using Gemini 3.5 Flash. A second opinion can be switched on by configuration, and is only worth doing when it is pointed at a genuinely different model — when two passes do run, their results are merged by averaging likelihood and magnitude and reconciling the direction labels. RC calls run sequentially (not in parallel) to manage rate limits and cost.

3. **Per-hazard triage grounding** — For each hazard, a separate web search grounding call is made using triage-specific queries (same three-tier backend: Brave → OpenAI → Gemini). These queries are explicitly different from the RC grounding: they focus on the current operational picture rather than structural change. Signal categories are SITUATION, RESPONSE, FORECAST, and VULNERABILITY. Recency windows are wider than RC but still focused: 60 days for ACE, FL, and TC; 90 days for DR. Source-priority lists in triage prompts elevate OCHA and humanitarian sources for the operational picture. The RC result is included in the triage grounding prompt so the search can be calibrated by what RC found — for example, if RC detected escalation, the triage grounding can focus on confirming or quantifying that escalation. Triage grounding calls also run in parallel across hazards.

4. **Per-hazard triage assessment** — For each hazard, the triage LLM is invoked with the triage grounding results, the RC result from step 2, and all relevant structured data for that hazard. The triage prompt is hazard-specific (see below). Triage runs a single pass by default, using Gemini 3.5 Flash, with the same optional second-opinion setting as RC. The ACLED low-activity filter is applied before ACE triage: if a country has 0 fatalities in the 2 most recent months and fewer than 25 fatalities in the trailing 12 months, ACE triage is skipped entirely and a default quiet score is assigned.

This architecture means each hazard gets four model-adjacent operations per country: an RC grounding search, an RC assessment, a triage grounding search, and a triage assessment. (Before July 2026 the two assessments each ran twice, for up to eight interactions; the second pass was found to be a word-for-word duplicate and was retired — see "Stabilization and tier assignment" below.) The grounding searches are run in parallel across hazards while the assessments are run one at a time, balancing throughput against cost control.

### Data sources injected into HS triage

The triage step receives the following data for each country–hazard pair:

- **Resolver features** — historical base-rate data from the facts_resolved table (all hazards).
- **RC result** — the output of the prior per-hazard RC assessment step, including likelihood, magnitude, direction, window, and rationale (all hazards). The RC result is presented as structured context with interpretation guidance: the triage prompt explains that triage_score and RC are "partially independent" — a country can have a high triage score (because the current situation is severe) but low RC (because the situation is chronic, not changing), or low triage but high RC (because a structural shift is emerging from a low baseline).
- **Triage grounding results** — hazard-specific grounded evidence from the triage web search call (all hazards).
- **Season context** — a human-friendly description of the current season for the region (all hazards).
- **ReliefWeb situation reports** — recent humanitarian reports from OCHA (all hazards).
- **ACAPS INFORM Severity** — crisis severity scores and trends (all hazards).
- **ACAPS Risk Radar** — forward-looking risk with triggers (all hazards).
- **ACAPS Daily Monitoring** — analyst-curated situational updates (all hazards).
- **ACAPS Humanitarian Access** — access constraint scores (all hazards).
- **Food security data** — FEWS NET IPC Phase 3+ population estimates (FEWS NET-monitored countries) and IPC API Phase 3+ estimates (non-FEWS NET countries) (all hazards).
- **NMME seasonal forecasts** — temperature and precipitation anomalies (climate hazards: DR, FL, TC).
- **ENSO state and forecast** — current ENSO conditions, Niño 3.4 anomaly, and 9-season probabilistic outlook from IRI/CPC (climate hazards: DR, FL, TC).
- **Seasonal TC forecasts** — basin-level seasonal activity predictions from TSR, NOAA CPC, BoM, Météo-France La Réunion (SWI), and the IMD/NIO climatology block, mapped to the country's basin(s) (TC only).
- **HDX Signals** — automated crisis alerts from OCHA, filtered by country and hazard (all hazards).
- **ACLED summary** — monthly aggregate conflict data (ACE only).
- **ACLED political events** — event-level political incidents (ACE only).
- **VIEWS + conflictforecast.org + ACLED CAST** — quantitative conflict predictions, including CAST's event-type disaggregation (ACE only).
- **ICG CrisisWatch** — per-country directional assessments and "On the Horizon" flags (ACE only).

### Per-hazard triage prompts and scoring anchors

Each hazard type receives a tailored triage prompt with hazard-specific scoring guidance. The prompts share a common preamble that explains the relationship between triage_score and RC — emphasizing that they are partially independent assessments — and then provide hazard-specific scoring anchors that tie numeric triage scores to concrete impact levels. For example:

- **ACE triage** anchors: 0 fatalities in window → 0.02–0.10; 1–9 fatalities → 0.10–0.30; 10–99 → 0.30–0.55; 100–999 → 0.55–0.75; 1,000–9,999 → 0.75–0.85; 10,000+ → 0.85–1.00.
- **DR triage** anchors: no food security concern → 0.02–0.10; moderate rainfall deficit → 0.15–0.35; IPC Phase 3 in multiple areas → 0.40–0.60; widespread crop failure → 0.60–0.80; famine declared or imminent → 0.80–1.00.
- **TC triage** anchors: out-of-season and no formation → 0.02–0.10; active season but no current threat → 0.15–0.30; tropical storm approaching → 0.35–0.55; major hurricane/typhoon threatening → 0.60–0.80; catastrophic landfall imminent → 0.80–1.00.

All triage prompts specify a priority ordering for scoring inputs: (1) current situation evidence, (2) RC result and direction, (3) seasonal context, (4) structural exposure and historical base rates, (5) vulnerability and capacity factors. This ordering prevents the LLM from defaulting to structural vulnerability when active situation evidence should dominate, while still giving weight to chronic risk factors when current signals are absent.

### ACLED low-activity filter

To prevent wasted LLM calls and false-positive ACE scores, the triage step applies a low-activity filter before running the ACE assessment. A country is filtered out if it meets both conditions: (a) 0 reported fatalities in the 2 most recent months of ACLED data, AND (b) fewer than 25 total fatalities in the trailing 12 months. Filtered countries receive a default quiet triage score without an LLM call. This filter saves cost and reduces noise for countries where armed conflict is structurally implausible (e.g., small island states or historically peaceful countries). The filter is conservative — 25 fatalities in 12 months is a low threshold — so it is unlikely to filter out countries with genuine emerging risk.

### Stabilization and tier assignment

RC and triage run a single pass by default (both on Gemini 3.5 Flash at temperature 0, which is already deterministic). The older two-pass averaging pattern remains available by configuration for anyone who wants to pair a genuinely different second model; running two identical passes was found to produce word-for-word duplicate outputs — doubling the cost and time of every scan for no gain — and was retired as the default in July 2026.

HS computes a tier label — quiet or priority — based on a single configurable threshold (default 0.50). Scores at or above the threshold are "priority"; scores below are "quiet". Tiers are intended for interpretability and prioritization, while the numeric triage_score is the primary signal that downstream components can use.

## 7. Regime Change (RC): per-hazard out-of-pattern detection

Regime Change is Fred's mechanism for flagging when base rates may be misleading in the forecast window. The intent is not to predict black swans on demand. Rather, it is to detect credible situations in which the generating process for a hazard may shift — for example, when a conflict enters a new phase, when a border policy changes, or when seasonal forecasts indicate unusually severe hazards.

RC is represented with three conceptual dimensions: likelihood, direction, and magnitude. Likelihood captures the chance that a regime shift occurs during the next 1–6 months. Direction indicates whether the shift would push outcomes up (worse), down (improving), mixed, or unclear relative to baseline. Magnitude captures how large the shift could be if it occurs.

### Per-hazard RC prompts and calibration

RC assessment now runs per-hazard with dedicated prompts for each hazard type. All hazard prompts share a common RC calibration preamble that sets conservative defaults: "Default to likelihood 0.05 and magnitude 0.05 unless evidence says otherwise." The preamble also specifies an expected distribution across all country-hazard assessments: roughly 80% should have likelihood at or below 0.10, roughly 10% between 0.10 and 0.30, roughly 7% between 0.30 and 0.55, and roughly 3% at 0.55 or above. This calibration guidance is critical for preventing score inflation — without it, LLMs tend to assign elevated RC to too many country-hazard pairs.

Each hazard type then receives its own specialized prompt content:

- **ACE (armed conflict)**: The RC prompt defines six categories of conflict early warning signals that the model should look for: (1) escalation signals (military buildup, arms flows, mobilization), (2) political triggers (election crises, coup attempts, government collapse), (3) social cohesion breakdown (ethnic/sectarian polarization, hate speech escalation), (4) economic shocks (currency collapse, severe austerity, resource competition), (5) external intervention shifts (foreign military involvement, proxy dynamics, sanctions changes), and (6) peace process disruption (ceasefire violations, negotiation collapse, spoiler activity). The ACE prompt also includes specific anchoring rules for ACLED data: the model is instructed how to interpret different levels of recent conflict activity in terms of RC likelihood. Conflict forecast data from VIEWS, conflictforecast.org, and ACLED CAST is injected alongside ICG "On the Horizon" alerts and HDX Signals.

- **DR (drought)**: The RC prompt emphasizes slow-onset dynamics and consecutive season analysis. It instructs the model to look for consecutive rainfall failures (one failed season is concerning; two consecutive failures are a strong RC signal), ENSO phase transitions (especially transitions into El Niño in regions where El Niño suppresses rainfall), IPC phase escalation (movement from Phase 2 to Phase 3+), and crop production disruptions. The ENSO state and probabilistic forecast are injected directly into the prompt, along with IPC data and HDX Signals for agricultural stress indicators.

- **FL (flood)**: The RC prompt focuses on GloFAS (Global Flood Awareness System) signals, upstream conditions, rainfall anomaly forecasts, and infrastructure degradation. It instructs the model to weigh seasonal timing heavily — flood risk is highly seasonal in most regions — and to consider ENSO phase effects on regional rainfall patterns. ENSO context is injected, along with NMME precipitation anomaly forecasts.


- **TC (tropical cyclone)**: The RC prompt includes a hard out-of-season rule: if the country is outside its historical cyclone season, RC likelihood must not exceed 0.03 regardless of other signals. During the active season, the prompt instructs the model to weigh the seasonal TC forecasts (from TSR, NOAA CPC, BoM, Météo-France La Réunion, and the North Indian Ocean climatology block) and ENSO state heavily, since ENSO phase is the strongest predictor of seasonal TC activity at the basin level. The seasonal TC context and ENSO context are both injected directly into the prompt.

All hazard-specific RC prompts accept a common set of data source sections through a shared formatting function. This function builds clearly labeled text blocks for: ReliefWeb situation reports, ACLED political events (ACE only), food security data (DR and ACE), ACAPS INFORM severity, ACAPS Risk Radar, ACAPS Daily Monitoring, and HDX Signals. Each block is only included when data is available for the given country and hazard.

### Separate RC grounding prompts

The RC grounding queries that feed the web search grounding call are now hazard-specific and separate from the triage grounding queries. RC grounding is designed to detect novelty — signals that the pattern may be changing — and uses three signal categories:

- **TRIGGER**: leading indicators of escalation or worsening (e.g., for ACE: military deployments, ceasefire violations, new armed group activity; for DR: consecutive rainfall failure, ENSO transition, crop production collapse).
- **DAMPENER**: counter-signals suggesting stabilization or de-escalation (e.g., peace talks progress, improved forecasts, humanitarian response scaling up).
- **BASELINE**: signals supporting continuation of current patterns (e.g., stable governance, normal seasonal progression, no change in structural factors).

Recency windows for RC grounding are shorter than for triage, reflecting RC's focus on recent disruptions: ACE uses 30 days, DR uses 60 days, FL uses 30 days, and TC uses 60 days. All RC grounding prompts include a source-priority list that favors wire services and specialist sources for novelty detection, and hazard-specific search labels (e.g., "armed conflict violence displacement humanitarian situation" for ACE) to improve search relevance.

### Data sources injected into RC assessment

RC assessment has its own dedicated prompt context for each hazard. The data injected includes:

- **RC grounding results** — hazard-specific grounded evidence from the RC web search call (all hazards).
- **Resolver features** — historical base-rate data (all hazards).
- **ReliefWeb situation reports** — recent humanitarian reports (all hazards).
- **NMME seasonal forecasts** — temperature and precipitation anomalies (climate hazards: DR, FL, TC).
- **ENSO state and forecast** — current ENSO conditions, Niño 3.4 anomaly, and 9-season probabilistic outlook from IRI/CPC (climate hazards: DR, FL, TC).
- **Seasonal TC forecasts** — basin-level seasonal activity predictions from TSR, NOAA CPC, BoM, Météo-France La Réunion (SWI), and the IMD/NIO climatology block (TC only).
- **HDX Signals** — automated crisis alerts from OCHA, filtered by hazard (all hazards).
- **ACLED summary** — monthly aggregate conflict data (ACE only).
- **ACLED political events** — event-level political incidents (ACE only).
- **ACAPS INFORM Severity** — crisis severity scores (all hazards).
- **ACAPS Risk Radar** — forward-looking risk assessments (all hazards).
- **ACAPS Daily Monitoring** — analyst-curated updates (all hazards).
- **VIEWS + conflictforecast.org + ACLED CAST** — quantitative conflict predictions (ACE only).
- **ICG CrisisWatch "On the Horizon"** — ICG's forward-looking conflict flags (ACE only). Countries flagged by ICG receive a prominent note, as ICG is highly selective about what it flags.
- **Food security data** — FEWS NET IPC and IPC API Phase 3+ population estimates (DR only).
- **ACAPS Humanitarian Access** — access constraint scores (all hazards, via triage data when available).

### Scoring and levels

Fred stores RC results as numeric and categorical fields in hs_triage. A derived RC score is computed as likelihood multiplied by magnitude. This provides a single 'how much should I care' number that suppresses cases that are high-likelihood but low-impact, or high-impact but highly speculative.

RC scores are mapped into discrete levels used for UI and downstream gating. Level 0 is base-rate normal, Level 1 is a watch state, Level 2 indicates elevated regime-change plausibility, and Level 3 indicates a strong out-of-pattern hypothesis. RC levels are now determined solely by the likelihood dimension: Level 0 (likelihood < 0.15), Level 1 (likelihood >= 0.15), Level 2 (likelihood >= 0.35), Level 3 (likelihood >= 0.55). The previous composite-score thresholds were removed in favor of this simpler, likelihood-only scheme. The per-hazard RC prompts include explicit calibration guidance: the expected distribution — roughly 80% of country–hazard pairs should have likelihood of 0.10 or below — and examples of what is and is not a regime change. A run-level distribution check warns operators when the fraction of elevated flags exceeds configurable thresholds (e.g., more than 15% at Level 2).

### Behavioral implications

Critically, RC does not merely decorate the dashboard. When RC is elevated, the system can override the 'need_full_spd' gating so that a full probabilistic forecast is produced even if the triage tier would otherwise be quiet. This is how Fred avoids an important failure mode: missing a structural break because it does not look like a high base-rate risk.

RC is surfaced to users across the dashboard: on country maps and lists as a 'highest RC' indicator, on triage tables as probability/direction/magnitude/score columns, and on question drilldown pages as summary boxes. This makes the system's out-of-pattern reasoning visible rather than hidden inside prompts.

## 8. Adversarial evidence checks: testing the RC hypothesis

A component added in March 2026, adversarial evidence checks provide a structured "devil's advocate" mechanism for elevated-risk forecasts. When Regime Change is elevated to Level 1 or above, the system automatically runs targeted web searches looking for counter-evidence — reasons the predicted regime shift might not materialize.

The adversarial check runs 2–3 targeted searches per elevated hazard, using hazard-specific search vocabularies. For example, if RC is elevated for armed conflict with an "up" direction (predicting escalation), the adversarial search looks for peace talks, ceasefire progress, and diplomatic resolution signals. If RC is elevated for drought, it searches for revised rainfall forecasts and improved water infrastructure.

The results are synthesized into a structured output with four components:

- **Counter-evidence**: specific claims with sources and relevance ratings that argue against the RC hypothesis.
- **Historical analogs**: past situations that appeared similar but did not result in the predicted regime shift, providing calibration.
- **Stabilizing factors**: structural or institutional factors that could prevent the shift from materializing (e.g., strong institutions, international engagement, resource buffers).
- **Net assessment**: an overall judgment of how strong the counter-evidence is (strong counter, moderate, weak counter, or inconclusive).

The adversarial check is stored in the database. It is both generated **and** injected into the forecasting prompt for every RC Level 1+ case, so the forecasting models always see the evidence against a regime shift alongside the evidence for it. Until July 2026 the check was generated at Level 1 but only injected at Level 2 and above — meaning that in a typical run most of these searches were paid for and then never shown to a forecaster. Level 2 and above additionally forces a full probabilistic forecast to be produced even if triage would otherwise have called the hazard quiet.

## 9. Hazard Tail Packs (retired July 2026)

Hazard Tail Packs were a second-stage evidence mechanism that ran extra web searches for high-RC hazards, looking for concrete leading indicators (TRIGGER), counter-signals (DAMPENER), and continuation signals (BASELINE). The section is kept, and numbered, so that older versions of this document on the About page still line up.

They were retired because two other mechanisms had come to cover the same ground. The adversarial evidence checks (Section 8) now run for every elevated-risk case and are injected into the forecasting prompt, and the Horizon Scanner's own per-hazard grounding evidence is now passed through to the forecaster directly. Tail packs were therefore paying for a third round of searching that largely duplicated the first two. Removing them cost the system no input.

One piece of vocabulary survives the retirement: the TRIGGER / DAMPENER / BASELINE signal categories are now the categories used by RC grounding itself (Section 7), which is where that framing does its work.

## 10. Question bank: what gets forecast and why

After HS triage, the system maintains a question set that defines what gets forecast. Conceptually, a question ties together: a country, a hazard, a metric, and a forecast horizon.

Questions are intended to be stable and comparable over time. They encode the metric to be forecast and the discrete bins that define the SPD outcomes. Four forecast metrics are supported: PA (people affected), FATALITIES (conflict fatalities), PHASE3PLUS_IN_NEED (IPC Phase 3+ population, used for DR in FEWS NET-monitored countries), and EVENT_OCCURRENCE (binary event probability for FL/DR/TC). The first three use SPD forecasts — discrete probability distributions over six buckets (PA and Phase 3+) or seven buckets (fatalities). Each metric's bottom bucket represents exactly zero impact (0 people affected, 0 fatalities, or 0 people in Phase 3+), so the forecast explicitly separates "nothing happens" from "a small event happens"; the next bucket starts at 1. Fatalities also has an extra top bucket for months with 1,000 or more deaths. EVENT_OCCURRENCE uses binary forecasts (single probability per month). This standardization is what enables scoring and calibration. Without it, each run would effectively forecast a different target.

The question set is typically refreshed using HS triage outputs. Priority-tier hazards are included by default, but as described earlier, elevated RC (level > 0) can force inclusion even for otherwise quiet hazards. This ensures the system pays attention to plausible regime breaks. Each question is assigned a track (see Section 12) based on its RC status: Track 1 for RC-elevated questions, Track 2 for priority questions without RC. The track determines the depth of the forecasting pipeline that the question passes through. A critical change in February 2026 made question IDs epoch-specific (e.g., `ETH_ACE_FATALITIES_2026-04`) and the questions table append-only: when a new HS run generates a question with the same ID as an earlier run, the original metadata (window start date, target month, wording) is preserved rather than overwritten. This prevents downstream resolution and scoring from breaking when the HS runs again months later. The question's own `window_start_date` is treated as authoritative for resolution — there is no LLM call log derivation or multi-tier fallback.

## 11. Prediction markets: crowd forecast signals (currently disabled)

Fred includes integration with three prediction market platforms: Metaculus, Polymarket, and Manifold Markets. The system uses search queries (generated by an LLM) and relevance filtering to find prediction markets that are thematically related to a given forecasting question — for example, a market about conflict escalation in a specific country might be relevant to an ACE question for that country.

**Note:** The prediction market retriever is switched off in both production workflows. Metaculus returns HTTP 403, Polymarket returns HTTP 422, and each call times out at 30 seconds, adding roughly 6 minutes of wasted waiting to every run. Note that it is the workflows, not the system's own default setting, that hold it off — so a newly written workflow or a local run will pick the retriever back up unless it explicitly disables it. It should not be re-enabled until the upstream APIs are fixed.

When enabled, prediction market signals are presented as contextual evidence, not authoritative data. They are embedded in forecasting prompts alongside structured data and other evidence. The rationale for including prediction markets is that they aggregate information from diverse participants with financial incentives to be accurate. However, market coverage is uneven — many humanitarian situations have no active prediction markets — and market liquidity varies widely. The system applies minimum thresholds (for example, minimum trading volume on Polymarket, minimum liquidity on Manifold) to filter out illiquid or unreliable markets.

## 12. Forecasting: SPD v2, ensembles, and structured evidence injection

Fred's primary forecast output is an SPD: a discrete probability distribution over outcome bins for each month in the horizon. This representation is more operationally useful than a point estimate because it preserves uncertainty and supports expected-value computations and tail-risk analysis. SPD data is stored in dual format: a numeric format (month index and bucket index with a probability value) for computational efficiency, and a labeled format (bin labels like "0" or "1-<10k" with a probability value) for human readability. Both representations are written simultaneously so that scoring and display can each use whichever is more convenient.

### Evidence injection

In the current architecture, the forecasting prompt receives a rich set of structured inputs rather than relying on LLM-generated research briefs. The forecaster does not use web-search evidence packs (those are reserved for the Horizon Scanner). Instead, it receives data from the structured connectors described in Section 4, along with several forecaster-specific inputs. The complete set of data injected into each SPD prompt is:

**Structured data from humanitarian APIs (loaded from the database for each country):**
- **ReliefWeb reports** — recent humanitarian situation reports (all hazards).
- **ACAPS INFORM Severity** — crisis severity scores and trend data (all hazards).
- **ACAPS Risk Radar** — forward-looking risk assessments with triggers (all hazards, when available).
- **ACAPS Daily Monitoring** — analyst-curated daily updates (all hazards, when available).
- **IPC phase data** — food security classifications with population counts per phase (all hazards, when available). Data comes from the unified food security loader which tries FEWS NET first and falls back to IPC API for non-FEWS NET countries.
- **FEWS NET Phase 3+ data** — IPC Phase 3+ population estimates from FEWS NET-monitored countries, loaded from the Resolver's `facts_resolved` table (all hazards, when available). This is the active food security data source. For DR/PHASE3PLUS_IN_NEED questions, FEWS NET "Most Likely" projection data is additionally injected directly into the SPD prompt, giving the model forward-looking IPC Phase 3+ context.
- **ACLED political events** — event-level political incidents (ACE hazards only).
- **HDX Signals** — automated crisis alerts from OCHA, filtered by country and hazard (all hazards).
- **VIEWS + conflictforecast.org + ACLED CAST** — quantitative conflict predictions and event-count forecasts (ACE only).
- **ICG CrisisWatch** — per-country directional assessments and "On the Horizon" conflict flags (ACE only).

**Climate and forecast data (loaded from the database or cache):**
- **NMME seasonal outlook** — temperature and precipitation anomalies for the next seven months (all hazards, via research data).
- **ENSO state and forecast** — current ENSO conditions, Niño 3.4 anomaly, and 9-season probabilistic outlook from IRI/CPC (climate hazards: DR, FL, TC).
- **Seasonal TC forecasts** — basin-level seasonal activity predictions from TSR, NOAA CPC, BoM, Météo-France La Réunion (SWI), and the IMD/NIO climatology block, mapped to the country's basin(s) (TC only).
- **GDACS event history** — historical disaster event records showing alert levels and population exposure by country-month (FL, DR, TC only). This provides structured base rate context for both SPD and binary forecast prompts.

**HS-derived context (from the prior Horizon Scanner run):**
- **HS triage output** — triage score, tier, RC fields (likelihood, magnitude, direction, score, level), and other structured assessments. This is the forecaster's primary link to the Horizon Scanner's judgment. Because the HS now runs per-hazard, the triage output passed to the forecaster reflects the hazard-specific assessment rather than a country-level aggregate.
- **Adversarial evidence check** — counter-evidence to the RC hypothesis, including historical analogs and stabilizing factors (RC Level 1+).
- **HS grounding evidence** — the per-hazard web-search findings gathered during the risk scan (RC and triage grounding), passed through to the forecaster rather than re-searched.

**Forecaster-specific inputs:**
- **Resolver history summary** — historical distribution data (source, recent level, trend, data quality) from the Resolver.
- **Calibration advice** — per-hazard/metric guidance text generated from historical scoring performance (all hazards).
- **Hazard-specific reasoning block** — tailored forecasting instructions for the hazard type (all hazards).
- **Prediction market signals** — crowd forecasts from Metaculus, Polymarket, and Manifold. Currently switched off in production; see Section 11.

This evidence is presented to the forecasting models as structured text blocks, each clearly labeled with its source. The forecaster sees, for example, the latest ReliefWeb reports about the country, the ACAPS severity score and trend, the IPC phase populations, the NMME climate outlook, and any adversarial counter-evidence — all formatted for readability rather than raw data.

Note that some data sources available to the Horizon Scanner are not passed through to the forecaster. ACAPS Humanitarian Access and ACLED monthly summaries are used during HS triage and RC assessment but are not directly injected into the SPD prompt. ICG CrisisWatch data is injected into SPD prompts for ACE hazards via the structured data loader, in addition to its influence through the HS triage output and RC fields. ENSO state/forecast and seasonal TC forecasts are now injected into SPD prompts for their respective hazard types (see Section 4 summary table).

### Hazard-specific reasoning guidance

Each hazard type now receives tailored reasoning instructions in the forecasting prompt, replacing the earlier generic guidance. These instructions reflect the fundamentally different generating processes behind different hazards. For example:

- **Armed conflict (fatalities)**: Guidance on tail-risk coverage for conflict escalation, bucket calibration for fatality counts, how to weigh ceasefire dynamics, and how different conflict types (state-based, one-sided, non-state) produce different fatality patterns.
- **Flood**: Guidance on seasonal patterns, upstream conditions, infrastructure resilience, and how flood impacts can spike dramatically in a single event.
- **Drought (PA)**: Guidance on slow-onset dynamics, cumulative effects, food security linkages, and how drought impacts often peak months after conditions begin deteriorating.
- **Drought (PHASE3PLUS_IN_NEED)**: A dedicated reasoning block for FEWS NET IPC Phase 3+ forecasts, with guidance specific to food security population estimates: how FEWS NET analysis cycles create data gaps that should not be interpreted as improvement, how to interpret current vs. projected phases, and how Phase 3+ populations are bounded by national population.

This hazard-specific reasoning helps models apply appropriate mental models rather than treating all forecasts identically.

### RC guidance and accountability

SPD v2 includes a dedicated Regime Change guidance block. When RC is elevated, the forecaster is instructed that the base rate is less reliable and must either widen the distribution appropriately or rebut the regime-shift hypothesis.

To prevent hand-waving, SPD v2 requires accountability in the human-facing explanation: the forecaster must include a sentence beginning with "RC:" that states what was flagged, whether it was accepted, and how it affected the forecast. This makes the system's interaction between RC and the distribution explicit.

### Structured reasoning traces

Each forecasting model now emits a structured reasoning trace alongside its SPD probability distribution. The trace is a JSON object with the following structure:

- **`prior`**: The model's starting distribution before considering evidence. Contains the prior distribution itself — one probability per outcome bucket, matching the question's bucket count (six for people-affected and food-crisis questions, seven for fatalities) — and a rationale explaining why the model chose that starting point.
- **`updates`**: An array of evidence signals that shifted the distribution. Each update contains `signal` (description of the evidence), `direction` (up/down), `magnitude` (SMALL/MODERATE/LARGE), `delta` (one number per bucket showing how probability mass shifted — the shifts must sum to approximately zero, since mass is moved rather than created), and the running distribution after applying this signal, which must equal the previous distribution plus the shift within rounding.
- **`point_estimate`**: A human-readable point estimate (e.g., "~40 fatalities") and `point_estimate_bucket` (the bucket index it falls in), used as a consistency check against the final SPD.
- **`rc_assessment`**: Whether the model accepted, rebutted, or partially accepted the Regime Change flag.

Traces are stored in the `reasoning_trace_json` column on both `forecasts_raw` and `forecasts_ensemble` tables. They are validated automatically, on three dimensions: (1) prior consistency — whether the model's stated prior modal bucket matches the implied bucket from base rate data; (2) delta arithmetic — whether each update's delta sums to approximately 0 and whether `post_update_spd` equals the previous SPD plus the delta; (3) magnitude consistency — whether the claimed magnitude (SMALL/MODERATE/LARGE) matches the actual size of the delta. Each dimension receives a score (0-1), and a composite `trace_quality_score` is computed as 40% prior + 40% delta + 20% magnitude. Validation is purely diagnostic and never blocks a forecast.

For Track 1 questions (full ensemble), the complete trace is required — `prior`, `updates` (at least 2 signals), `point_estimate`, and `rc_assessment`. For Track 2 questions (single model), only `prior` and `rc_assessment` are required; the `updates` array may be empty and `point_estimate` is optional. Binary forecasts (EVENT_OCCURRENCE) do not produce reasoning traces — the `reasoning_trace_json` column is NULL for binary questions. Over time, accumulated traces feed into the calibration advice system, which can now diagnose whether models are anchoring appropriately on base rates or systematically over- or under-assigning probability to certain outcome ranges.

### Track-based routing

Not all questions require the same depth of forecasting. Fred uses a track system to route questions through different pipeline configurations based on their risk profile:

- **Track 1** questions are those where Regime Change is elevated (RC level > 0). These go through the full multi-model ensemble, which currently includes 5 models across 3 providers: GPT-5.6 Sol and GPT-5.6 Luna (OpenAI), Claude Opus 5 (Anthropic), and Gemini 3.1 Pro and Gemini 3.5 Flash (Google). Track 1 questions also receive scenario narratives (see Section 13). The rationale is that RC-elevated questions represent the highest-uncertainty situations where model diversity matters most.
- **Track 2** questions are priority-tier questions with no elevated RC signal. These use a lightweight single-model path (currently Gemini 3.5 Flash) that is faster and cheaper. Scenario generation is skipped. Track 2 reflects a practical judgment: when base rates are expected to hold, a single capable model produces adequate forecasts without the cost of running the full ensemble.

The track field is persisted in the database alongside triage and question records, so downstream analysis can distinguish how each question was processed.

### Ensemble aggregation

For Track 1 questions, the system aggregates member SPDs into named ensemble forecasts. The two named ensembles are `ensemble_mean_v2` (simple average of member SPDs) and `ensemble_bayesmc_v2` (a Bayesian Monte Carlo aggregation that weights models by their historical calibration performance). Named ensembles are tracked as explicit model names in the database, allowing the dashboard and scoring system to compare ensemble methods against individual models. Track 2 questions produce only a single `track2_flash` forecast row — no ensemble aggregation. The ensemble approach is a pragmatic response to model idiosyncrasies: it tends to reduce the chance that a single model's blind spot dominates a forecast.

### Binary forecasts (EVENT_OCCURRENCE)

In addition to SPD forecasts for magnitude-based metrics (PA, FATALITIES, PHASE3PLUS_IN_NEED), Fred produces binary forecasts for event occurrence questions. Binary questions ask whether a significant disaster event (GDACS Orange or Red alert) will occur in a given country-hazard-month, rather than estimating the magnitude of impact.

Binary questions are generated for FL (flood), DR (drought), and TC (tropical cyclone) hazards across all countries, using GDACS global coverage. The binary prompt builder constructs a dedicated prompt that includes seasonal base rates (computed from historical GDACS event records), current situation context, GDACS event history showing past alert patterns, and hazard-specific reasoning guidance. Each model outputs a per-month probability of event occurrence, which is stored using the SPD storage convention: bucket 1 holds P(event), bucket 2 holds P(no event) = 1 - P(event), and the remaining buckets are zero.

Binary forecasts are scored using Brier score only (not log score or CRPS, which require a full distribution). On the dashboard, binary questions display as probability bars per month rather than SPD distributions, with resolution outcomes showing whether a qualifying event actually occurred. The risk index for EVENT_OCCURRENCE returns the raw probability (0-1) rather than computing expected impact values.

### Self-search (disabled)

The system includes a self-search capability where the model can request a single additional web query when evidence is insufficient. However, self-search is disabled by default along with the deprecated web research pipeline. Turning it on requires three separate settings to be enabled together — a deliberate safeguard, since a prompt that offers models an evidence-request option the system will then refuse is worse than not offering it at all. It is not used in production.

## 12b. Sibyl: the parallel deep-research track

Sibyl is a second, deliberately independent way of answering Fred's hardest questions. Where the standard forecasting track reasons over the structured data feeds Fred has already ingested into its database, Sibyl sends an AI research agent out onto the open web to build its own picture from scratch. Running the two tracks side by side turns every disagreement between them into information: if deep research and the structured-data ensemble land in very different places, something about that question deserves human attention.

### Which questions Sibyl takes on

Sibyl does not forecast everything. After each Horizon Scanner run it selects the ten questions where the underlying situation looks most volatile — using the Regime Change score, which measures how likely a country-hazard is to break from its historical pattern — restricted to the numeric "how many people" questions: conflict fatalities (armed conflict), people affected (floods and cyclones), and the food-crisis population (drought). Yes/no event questions are excluded. Questions are worked through in descending volatility order, so if the spending cap bites mid-run, the least informative work is what gets sacrificed.

### How a Sibyl forecast is made

For each question, Sibyl runs three independent research investigations ("trials"). Each trial works like a disciplined human forecaster:

1. It starts from the **outside view** — the historical base rate for that country and hazard from Fred's own Resolver database (seasonal patterns for floods and cyclones, the recent trajectory for conflict, recent assessments for food crises). This anchor is the *only* input Sibyl shares with the standard track, and the agent is explicitly told it is a starting point to reason away from, never a target.
2. It then gathers the **inside view**: step by step, the agent chooses a web search or reads a page it found, and after every step it must restate its full belief — its probability estimates, the evidence pushing the number higher, the evidence pushing it lower, what it still doesn't know, and how its current estimate relates to the base-rate anchor. This running "belief state" is the agent's memory; it never accumulates a pile of raw articles.
3. After at most ten steps (or earlier, once more research would not change its mind), it submits a final distribution expressed as quantiles — "10% chance the monthly figure is below X, 50% below Y, 99% below Z".

The three trials are given different analytical perspectives (base-rate-weighted, tail-risk-sensitive, recent-signal-driven) so they genuinely explore different readings of the evidence. Their three distributions are then pooled by averaging the probability curves — a method chosen because it *widens* the combined forecast when the trials disagree, which is exactly the honest response on a volatile question. The pooled distribution is converted into the same probability buckets the standard track uses and stored alongside the standard forecasts, so the existing scoring and calibration machinery grades both tracks head-to-head with no special handling.

### Keeping the comparison honest

Two safeguards protect the experiment's integrity. First, the research agent is blocked from reading the data sources Fred uses to grade forecasts (ACLED, IFRC GO, IDMC, GDACS, FEWS NET, IPC) — it must work from open reporting, not from the answer key. Second, for retrospective evaluations every search is date-capped at the forecast's "as of" date, and a filter drops any retrieved material published after that date, with the residual leak rate logged for audit. The same date cap is applied in live runs too, where it is harmless.

### Cost control

Deep research is expensive — roughly a dollar or two per question — so Sibyl is expected to dominate Fred's API spend. A hard cap (default $40 per run, roughly three times the expected cost) is checked before every new question and between every trial: once crossed, no new work starts, everything already completed is saved, the remaining questions are marked "skipped: run budget cap", and the run is flagged as budget-capped on the dashboard. Because a model call's cost is only known after it returns, the unit in flight when the cap is crossed finishes first — so actual spend can overshoot the cap by about one question's cost, by design. All Sibyl spend appears in the regular Costs page, itemised into Opus tokens and Brave search credits.

### What you see on the dashboard

A dedicated Sibyl page shows each run's coverage (which of the ten questions were forecast, skipped, or capped), total cost, and — most usefully — a table of questions sortable by how far Sibyl's distribution diverges from the standard track's (measured by Jensen–Shannon divergence, where 0 means identical and higher means more disagreement). Expanding a question overlays the two distributions, shows each trial's quantiles, and exposes every trial's full step-by-step reasoning trace: what it searched, what it read, what changed its mind, and how it reconciled the evidence with the base rate. The run summary page shows Sibyl's coverage and budget status beside the standard track's own numbers, and the main risk-index map gains a toggle to view the Sibyl forecasts where they exist.

Sibyl's accuracy is deferred judgment: a per-hazard recalibration hook exists but stays switched off until enough Sibyl forecasts have resolved to measure whether its distributions run too narrow or too wide.

## 13. Scenarios, narratives, and human interpretability

In addition to numeric forecasts, Fred can produce scenario narratives for Track 1 questions (those with elevated RC). Scenarios are not treated as forecasts in their own right. They are interpretability artifacts meant to summarize plausible pathways that could lead to different bins of the SPD. Scenario generation is skipped for Track 2 questions, where the base rate is expected to hold and the additional interpretive cost is not warranted.

Scenario narratives are particularly useful when RC is elevated, because they help users understand what a regime shift would look like operationally. However, narratives are also easy to misuse. Fred therefore keeps scenarios optional and separates them from the numeric forecasting artifacts used for scoring.

## 14. Scoring, calibration, and evaluation loops

A forecasting system is only as good as its evaluation loop. Fred includes workflows to compute resolutions (ground truth), compute forecast scores, assess calibration, and — in the latest version — generate calibration advice that feeds back into the forecasting prompts.

### Horizon-specific scoring

A critical correctness fix in February 2026 changed scoring to be horizon-specific: each of the six forecast months is now scored against its own calendar month's ground truth, rather than all six being scored against a single target month. For example, if a question's forecast window starts in September, month 1 is scored against September data, month 2 against October data, and so on through month 6 against February data. The resolutions table stores one row per (question, horizon month) pair, with the resolved ground-truth value and the calendar month it corresponds to.

Resolution uses source-aware null handling: not all horizons will necessarily have ground truth. For FATALITIES (ACE) and EVENT_OCCURRENCE, if no data exists for a given month the system defaults to 0, because ACLED has continuous coverage and GDACS has global coverage — absence of data genuinely means no events. For PA (people affected) and PHASE3PLUS_IN_NEED, horizons with no data are left unresolved rather than defaulted to zero, because IFRC and FEWS NET do not report on every country-month — absence of data means "unknown," not "zero impact." Unresolved horizons are excluded from scoring, so they do not artificially inflate or deflate model performance. This means some questions may show scores for fewer than six horizons on the Performance page.

### Scoring rules

Three proper scoring rules are computed for each scored SPD forecast: the Brier score (sum of squared differences between predicted probabilities and the one-hot truth vector; lower is better), the log score (negative log of the probability assigned to the true bin; heavily penalizes confident wrong predictions), and a CRPS-like score (compares the cumulative distribution against a step function at the true bin). All three metrics are stored per (question, horizon, model) and are aggregated into averages and medians on the dashboard. Binary questions (EVENT_OCCURRENCE) are scored using Brier score only: the square of the difference between the forecast probability and the binary outcome (event = 1, no event = 0). Log score and CRPS are not computed for binary questions because they require a full multi-bucket distribution.

### Benchmarking against ViEWS

Scoring Fred against itself only says whether it is improving. To know whether it is any *good*, its conflict forecasts are also scored against an established external benchmark. Every scoring cycle, the VIEWS conflict predictions Fred already ingests (Section 4) are converted into distributions over Fred's own fatality buckets and graded with exactly the same rules, on exactly the same questions and months, as Fred's own forecasts. The result appears on the Performance page as an extra row labelled "ViEWS (external benchmark)", directly comparable to the ensemble and to each individual model.

Two caveats matter when reading that row. VIEWS publishes a point prediction rather than a distribution, so turning it into one requires assumptions that are Fred's, not VIEWS's — the comparison is indicative, not a formal head-to-head between two distributional forecasters. And it covers conflict fatalities only, because that is the metric VIEWS forecasts. Within those limits it answers the question a forecaster actually wants answered: is the ensemble beating the best publicly available machine-learning baseline for this hazard, or merely beating its own past self?

### Calibration weights

Calibration weights are computed per model, per hazard, and per metric. The system uses an exponential half-life weighting scheme (with a 12-month half-life) so that more recent forecast performance is weighted more heavily than older results. A minimum number of scored questions (currently 20) is required before calibration weights are considered valid. These weights are used by the Bayesian Monte Carlo ensemble aggregation to give more influence to models with better historical performance on similar questions.

### Calibration advice

New in March 2026, the system generates human-readable calibration advice per hazard, metric, and model. Because each forecasting model has distinct tendencies — one model may under-weight tail risk for conflict while another is overconfident on drought — calibration advice is now model-specific, stored with a model name and advice version. This advice is based on analysis of historical forecast performance — for example, it might note that a particular model has historically assigned too little probability mass to the highest outcome bins for armed conflict fatalities, or that drought forecasts from another model tend to be overconfident in months 4–6. Calibration advice is stored in the database and injected into forecasting prompts, creating a feedback loop where past scoring performance directly informs future forecasts. For hazards or metrics where insufficient scored data exists, seed advice (based on domain knowledge) is used until enough performance data accumulates.

### Workflow ordering

The calibration workflow chain runs in a specific order: Resolver backfill, then Compute Resolutions, then Compute Scores, then Calibration (including advice generation). This ordering was fixed in February 2026 to prevent scores from running before resolutions were available.

### The scored-forecast analysis bundle

At the end of every calibration round, the system packages a single downloadable report bundle designed to be handed to an AI analyst (added July 2026). For every question that has been scored, the bundle pairs everything that went into the forecast with what actually happened: the exact prompt each model received (which contains all the injected data), each model's full written response and step-by-step reasoning, the Horizon Scanner's regime-change rationale and the web evidence it gathered, and then the realized outcome, the source that resolved it, and every score. It also includes flat score tables, the calibration weight movements and advice, and a set of pre-selected "case studies" — the best and worst scored questions — so reasoning patterns behind good and bad forecasts are easy to compare side by side. A built-in analyst guide explains the file layout, the scoring scales, and known caveats, so an AI reading the bundle needs no other context. A small "briefing" folder inside the bundle holds condensed versions sized for pasting into a chat conversation. The goal is a repeatable improvement loop: after each scoring round, download one file, give it to an AI, and get back concrete suggestions about where the forecasting process is systematically going wrong.

## 15. Dashboard and user interface

Fred's dashboard is designed for two audiences: forecasters (who need to inspect evidence and produce forecasts) and decision-makers (who need a summary of risk and tail conditions).

Key dashboard pages include: the Forecast Index (country-level rollups and map), the Countries list and drilldowns, HS Triage, Forecast lists and drilldowns, Sibyl (the deep-research track), Resolver (data inspection), Costs, Performance, Downloads, and About.

RC is a first-class UI concept. Countries with Level 1-3 RC flags are highlighted, and questions display RC probability/direction/magnitude/score so users can see when the system believes a base-rate deviation is plausible. The question detail page includes a regime-change summary panel showing the RC rationale, identified triggers, confidence assessment, and key metrics. Exports include RC fields so that analysis outside the dashboard preserves the same context.

The question detail page also includes an LLM transcript viewer that displays the full prompts and model responses grouped by pipeline stage (grounding, RC, triage, SPD). This allows operators to inspect exactly what each model was asked and how it responded, supporting the system's auditability goals. For binary (EVENT_OCCURRENCE) questions, a dedicated BinaryPanel displays per-month probability bars, resolution outcomes (event vs. no event), and per-horizon Brier scores.

The Resolver page exists because the system treats data provenance as a primary concern. It is designed as a source-level accordion data explorer grouped by category (Resolution Data, Conflict Forecasts, Weather and Climate, Situation Reports, Other Alerts, Other). Each data source gets a collapsible row showing summary metadata (name, last updated, global and country row counts). Expanding a row reveals the source's data table, lazy-loaded on demand. A shared country selector at the top filters all country-filterable sources. This design lets users inspect exactly what data is feeding their country's forecasts without navigating between multiple tabs.

The About page includes versioned snapshots of both the system's prompts and this system overview document. Users can select from a dropdown of dated versions to see how the system's documented behavior has evolved over time. This supports auditability: when investigating a historical forecast, operators can review the prompt and system configuration that were active at the time.

The Performance page surfaces forecast evaluation in the dashboard, and is split into two tabs: a Dashboard tab with the live numbers, and an "About performance scores" tab explaining each scoring rule in both technical and plain terms, with its range and what a good value looks like.

The Dashboard tab has four sections. **Summary** shows KPI cards — resolved questions (as a share of those actually eligible to resolve yet), scored questions across all tracks, the Track 1 / Track 2 split, hazards, models, and ensemble accuracy. **Resolution Coverage** shows resolution rates by hazard and metric, colour-coded by completeness (green above 90%, yellow 50–90%, red below 50%); questions too new to have resolved yet are counted separately and shown as "awaiting first horizon" rather than being scored as a failure. **Sibyl — Deep-Research Track** compares the deep-research track head-to-head with the standard one on the exact set of questions Sibyl covered (Section 12b). **Detailed Scores** supports four views — Total, By Hazard, By Run, and By Model — filterable by metric scope (people affected, fatalities, event occurrence, or Phase 3+), with an ensemble selector for comparing aggregation methods.

Two details matter for reading the score tables correctly. Binary and magnitude accuracy are shown in **separate** columns ("SPD Brier" and "Binary Brier"), each with its own question count, because they sit on different scales and averaging across them is meaningless. And both average and median values are shown for every scoring rule; medians are particularly useful because they are less sensitive to outliers from early-run or data-sparse questions.

The Downloads page was expanded to include performance score exports: per-question CSV files for each named ensemble (including the full 6-month forecast grid across up to 7 bins, expected impact values, resolution values, and scores), a model-level summary CSV with average, median, min, and max scores per model and hazard, and a rationale export. The rationale export downloads the human-readable explanations that each forecasting model provides alongside its probabilistic forecast. These explanations are extracted from the `human_explanation` field in the model's JSON response and include the model's stated reasoning about the base rate, key evidence signals, and its response to the Regime Change flag. Rationale exports can be filtered by hazard code to focus on a specific hazard type.

## 16. Operations: canonical DB artifacts, workflows, and debugging

Fred is typically operated through GitHub Actions. Workflows download a canonical database artifact, apply new computations, and re-upload an updated artifact. A concurrency lock prevents multiple workflows from mutating the canonical DB at the same time. Model configuration is centralized in a single ensemble list, where each entry specifies a provider and model identifier (for example, OpenAI's GPT-5.6 Sol or Anthropic's Claude Opus 5). To change the models used in production, operators edit this list — no code changes are needed. Purpose-specific overrides (for example, a cheaper model for scenario writing or an HS fallback model) are also configured in the same file. Model cost rates (input and output cost per 1,000,000 tokens, the industry-standard unit) are stored separately so that costs can be updated by editing data rather than code.

Scheduled workflows include: one for refreshing ICG CrisisWatch data (several times in the first days of each month, when ICG publishes, reading the Internet Archive's copy of the CrisisWatch page), the primary backfill workflow (28th of each month, running all data connectors in five sequential phases), and a mid-cycle structured data refresh (weekly on Sunday 03:00 UTC) that updates fast-changing sources — conflict forecasts, GDACS, ReliefWeb, ACLED political events, and GDELT. ENSO and the seasonal cyclone outlooks once had standalone refresh workflows of their own; those were removed in July 2026 because they only produced a throwaway file that nothing read. Both are now fetched and stored as part of the monthly backfill's context phase, which is where the forecasting pipeline actually reads them from. The mid-cycle refresh ensures that these rapidly-evolving data sources stay current between monthly backfills, so forecasts made mid-month benefit from the latest conflict and disaster data. The monthly backfill deliberately runs on the 28th, a few days before the monthly forecast run on the 1st: it is the only refresh for the sources the system later scores its forecasts against (conflict fatalities, disaster impacts, displacement, food insecurity), so it has to land before the forecast rather than after it. Until early August 2026 it ran on the 15th instead — two weeks after the forecast it was meant to feed — which meant each month's forecasts reasoned over core data that was already more than two weeks old. Running it on the 28th also means the system finishes scoring and recalibrating itself immediately before the next forecast, so each round of forecasts uses the freshest available performance weights. The primary backfill workflow includes all data sources: Resolver connectors (ACLED, IDMC, IFRC), resolution sources (FEWS NET IPC, IPC API, GDACS), structured data (conflict forecasts, ACAPS, ReliefWeb, ACLED political, NMME), and context sources (ENSO, seasonal TC, HDX Signals, CrisisWatch). NMME ingestion, previously a standalone workflow, is now a step within the structured data pipeline (with graceful handling for the fact that CPC FTP files are published around the 9th–10th of each month). All scheduled workflows run on independent schedules and write to the canonical database or cached JSON files that the HS pipeline reads at runtime. This decouples data refreshes from the HS run itself, ensuring that fresh data is available even between HS runs and that individual scraper or API failures do not block the main pipeline.

A signature guardrail is used to ensure the database contains required tables before being treated as canonical. This protects against partial artifacts and prevents downstream stages from running on an incomplete database.

Debugging is treated as an operational requirement. Runs log LLM calls, costs, evidence pack diagnostics, and the reasons why certain questions were included or skipped. A comprehensive debug bundle can be generated that includes triage summaries, research briefs, forecast details, and scoring results for a given run. This makes it feasible to answer "why did the model think this?" after the fact.

## Test Mode

Test mode allows the team to run the full Pythia pipeline without contaminating production data. When a pipeline run is started in test mode, every piece of data it produces is automatically tagged as "test data."

The website hides test data by default. A toggle in the navigation bar labeled "Test ON/OFF" lets users choose to view test data alongside production data. When the toggle is on, an amber banner warns that test data is being displayed.

Calibration and performance scoring use only production data — test runs cannot influence the system's self-tuning.

If a run was mistakenly executed without test mode enabled, it can be retroactively marked as test data using a maintenance tool, without needing to re-run the pipeline.

## 17. Practical guidance for forecasters

The system is designed to support, not replace, human judgment. In practice, forecasters should treat HS triage as a prioritization and hypothesis-generation tool. The most productive workflow is: (1) inspect HS triage and RC flags; (2) review the structured data feeds (ReliefWeb reports, ACAPS assessments, IPC phases, ENSO conditions, seasonal TC outlooks, HDX Signals alerts) and the grounding evidence gathered for high-RC hazards; (3) check the adversarial evidence to understand counter-arguments; (4) decide what would move the distribution; (5) ensure the SPD expresses both the baseline and the plausible tail mechanisms; and (6) write explanations that are accountable and falsifiable.
