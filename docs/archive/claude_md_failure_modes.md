# Archived: CLAUDE.md known failure modes

These post-mortems were moved out of the root [`CLAUDE.md`](../../CLAUDE.md) when that file
reached ~75k tokens and half of it was history. They are **verbatim**, in their original order.

They were archived because each describes a bug that is fixed and whose current behaviour is
now stated in a CLAUDE.md reference section — not because the lesson stopped mattering.
**Every `**Rule:**` line these entries taught is preserved in CLAUDE.md's `## Invariants`
section.** Read this file when you want the full story behind an invariant, when you suspect a
regression in one of these subsystems, or before re-reporting something that may already have
been diagnosed here.

Entries that still describe live behaviour, live policy, or live recovery steps stayed in
CLAUDE.md and are not duplicated here.

---

- **Writers assigned month_index by sort position, not by label** (fixed): `_write_spd_outputs`, `_write_binary_outputs`, and `_write_spd_members_v2_to_db` used `enumerate(sorted(labels))` to assign `month_index` 1..6. Any missing or hallucinated off-window month label silently shifted every subsequent month against resolutions. All three writers now map each label to its horizon index via `_month_index_for_label(label, anchor_month)` (calendar labels → offset from window start; `month_N` → N) and drop unmappable/off-window labels with a `[warn]` log. The binary pipeline additionally filters parsed model months to the expected window before aggregation.
- **Binary NULL-model ensemble score was nondeterministic; NULL-model convention retired** (fixed): the binary path in `compute_scores.py` read the ensemble P(yes) from `forecasts_ensemble` with no `model_name` filter, ordered only by `created_at` — so when both `ensemble_mean_v2` and `ensemble_bayesmc_v2` rows existed, the NULL-model score row could be either, and it always duplicated the named aggregate row scored from `forecasts_raw` (double-counting in any consumer that averaged across model_names). An interim fix added a deterministic model_name preference; the July 2026 scoring-hardening PR then retired NULL-model score rows entirely — every score row (SPD and binary) is keyed by an explicit `model_name`, with aggregates under `ensemble_mean_v2`/`ensemble_bayesmc_v2`/`track2_flash`. The dead legacy writer `_write_spd_ensemble_to_db` and the `_load_spd(table="ensemble")` read of the never-populated `horizon_m/class_bin/p` columns were deleted; `generate_calibration_advice` classifies aggregates by name (legacy `'__ensemble__'` rows from old DBs still recognized).
- **CRPS was a nonstandard /K variant** (fixed): `_crps_like` summed squared CDF differences over all K buckets (the K-th term is identically 0) and divided by K=5, deflating scores 20% vs the standard and making literature comparison invalid. Replaced by `_rps`: `Σ_{k=1..K−1}(F_k−H_k)²/(K−1)`, the standard normalized Ranked Probability Score, range 0–1, still stored under score_type='crps' (dashboard/CSV plumbing unchanged; `_crps_like` remains as an alias for `score_views.py`). Scores computed before this change are on the old scale — the DB was archived at the same time, so fresh scores are consistently on the new scale.
- **Zero-defaults had no left-edge/gap coverage guard** (fixed): FATALITIES+ACE and EVENT_OCCURRENCE horizons defaulted to 0 for any month ≤ the freshness cutoff, including months inside ingestion gaps or before the source's coverage began — false zeros that then trained calibration. `_months_with_source_data()` in `compute_resolutions.py` now gates zero-defaulting to calendar months where the source has at least one row globally; uncovered months stay unresolved.
- **Calibration weights computed but never used; aggregates polluted the weight pool** (fixed): the per-model softmax in `compute_calibration_pythia.py` included score rows for `ensemble_mean_v2`/`ensemble_bayesmc_v2`/`track2_flash`/NULL — aggregate outputs competing against their own members (and usually winning, diluting every member weight). These are now excluded via `AGGREGATE_MODEL_NAMES`; binary pools (which contain only aggregate rows, since per-member binary forecasts are not stored) produce no weights with an explanatory note. On the consumption side, `_load_calibration_weights_db` in `forecaster/cli.py` previously had **no callers** — weights are now resolved per (hazard, metric) via `_resolve_member_weights()` (cached per process, name-matched against both plain spec names and the disambiguated `Name (model_id)` form, rescaled to mean 1.0) and applied to both the BayesMC evidence weights and a weighted `aggregate_spd_v2_mean`. Gated by `PYTHIA_USE_CALIBRATION_WEIGHTS` (default `1`); members without a stored weight get 1.0, and if nothing matches the aggregation silently stays unweighted.
- **Calibration pipeline silently no-ops on DuckDB 1.5.2 due to transaction-aborted state** (fixed): `compute_calibration_pythia.py` and `generate_calibration_advice.py` both used the pattern `try: conn.execute("ALTER TABLE ... ADD COLUMN ..."); except Exception: pass` to make migrations idempotent. On DuckDB 1.4.4 (developer machines) this worked — a failed DDL in an auto-commit transaction simply rolls back and the connection continues. On DuckDB 1.5.2 (GitHub runners), the same failed DDL leaves the connection in an aborted-transaction state; the next statement (a `PRAGMA table_info(...)` call inside `_table_exists`) raises `TransactionContext Error: Current transaction is aborted (please ROLLBACK)`, which is caught by the same broad `except` and returned as `False`. Effect: every calibration run logged `compute_calibration_pythia: scores table not found; nothing to do.` and `generate_calibration_advice: table scores not found; skipping.` despite the DB containing thousands of score rows. `latest_calibration` stayed `null`; `calibration_weights`/`calibration_advice` stayed empty. Fixed by replacing every "ALTER ADD COLUMN inside try/except" with an `_add_column_if_missing(conn, table, col, type)` helper that checks `PRAGMA table_info` first and only ALTERs when missing; added a `_rollback_quietly(conn)` call in the `except` paths of `_table_exists` / `_row_count` / `_column_exists` to scrub residual aborted-state. Also fixed Bug 2: `compute_calibration_pythia.py`'s `CREATE TABLE IF NOT EXISTS calibration_advice` used the legacy 3-column PRIMARY KEY `(as_of_month, hazard_code, metric)` instead of the 4-column form in `pythia/db/schema.py` — dormant on existing DBs (CREATE IF NOT EXISTS is a no-op) but would re-trigger the dual-constraint failure on a fresh DB. Also fixed Bug 3: `.github/workflows/compute_calibration_pythia.yml` only ran the EMA centroid update for `--metric PA` and never seeded `bucket_centroids` from `BUCKET_SPECS`; now seeds first via `python -m scripts.db.update_bucket_centroids` (uses `PYTHIA_DB_URL` env var), then loops EMA over PA/FATALITIES/EVENT_OCCURRENCE/PHASE3PLUS_IN_NEED with `|| echo WARN` so insufficient-data metrics don't fail the workflow. Workflow now also uploads a `calibration-summary` artifact (`calibration_summary.json` with row counts for `resolutions`/`scores`/`bucket_centroids`/`bucket_definitions`/`calibration_weights`/`calibration_advice`) so future failures are visible at-a-glance instead of buried in step logs.
- **EMA centroid update duplicate-key crash** (fixed): `update_bucket_centroids_ema()` in `pythia/tools/compute_bucket_centroids.py` crashed with `ConstraintException: Duplicate key "hazard_code: TC, metric: PA, bucket_index: 1" violates unique constraint` on the second (and later) monthly calibration run. The `ux_bucket_centroids` unique index is on `(hazard_code, metric, bucket_index)` — it does NOT include `as_of_month` — but the EMA `DELETE` filter matched on `as_of_month = ?` so the previous month's row for the same (hazard, metric, bucket) was left in place and the INSERT violated the unique constraint. Fixed by broadening the `DELETE` to match any `as_of_month` for that (hazard, metric, bucket_index) before inserting the new row. Net effect: bucket_centroids keeps one row per (hazard, metric, bucket_index), with the `as_of_month` stamp reflecting the most recent EMA update.
- **DuckDB cache key mismatch** (fixed): The DuckDB connection pool was using raw URL strings rather than resolved paths as cache keys, causing 100+ `cache_event=miss` entries and a new connection per DB access. Fixed by normalizing to resolved paths.
- **API stale DB connection after sync** (fixed): `_ensure_read_connection()` in `app.py` cached a singleton DuckDB connection forever. When `maybe_sync_latest_db()` atomically replaced the DB file on disk (`os.replace()`), the open connection still read from the old file descriptor (Unix inode semantics). New pipeline runs were invisible to the dashboard until the API process restarted. Fixed by adding `_maybe_refresh_db()` to `_con()`: it periodically (every 60s) calls `maybe_sync_latest_db()` and, if a new DB was downloaded (signalled via `db_was_refreshed()` flag in `db_sync.py`), closes the old connection and opens a new one.
- **API stale DB connection after sync — flag-only gate unreliable** (fixed): The fix above gated the reopen solely on `db_was_refreshed()`, a consume-once `threading.Event`. On Render the API serves many requests concurrently; any request path that consumed the flag before `_maybe_refresh_db()` ran (e.g. a prior `/v1/version` call which itself invokes `maybe_sync_latest_db`) prevented subsequent requests from ever reopening `_READ_CON`. Symptom: `/v1/version` reported the NEW `db_sha256` but every data endpoint (e.g. `/v1/resolver/source_inventory`) kept returning rows from the pre-refresh DB. Fixed by also gating reopen on DB file mtime: `_READ_CON_MTIME` is captured when the connection opens, and `_maybe_refresh_db()` reopens whenever `os.path.getmtime(db_url) > _READ_CON_MTIME`. Idempotent — the flag path still wins on the worker that performed the download; mtime rescues all other workers/paths.
- **`/v1/admin/force_sync` had the same flag-only blind spot** (fixed): The mtime-fallback fix above was applied to `_maybe_refresh_db` (the periodic check used by `_con()`), but the explicit `/v1/admin/force_sync` admin endpoint still reopened the connection only when `db_was_refreshed()` returned `True`. If another concurrent request (e.g. a `/v1/version` poll) consumed the consume-once flag between the sync and the reopen-decision, force_sync would download a fresh DB, never reopen `_READ_CON`, and return `{"db_refreshed": True}` even though the connection remained pinned to the pre-sync inode. After a real publish (May 6: release went from `db_sha256=224038cc…` / max hs_runs.generated_at=2026-03-13 to `db_sha256=4e732c80…` / max=2026-05-01), `/v1/admin/force_sync` left the dashboard reading stale data. Fixed by mirroring `_maybe_refresh_db`'s gate: reopen on `flag_refreshed OR mtime_newer`. The endpoint now also returns the individual `flag_refreshed` and `mtime_newer` booleans so the caller can verify why the reopen happened (or didn't).
- **API frozen on stale DB by a wedged temp path (`[Errno 21] Is a directory`)** (fixed): `download_db_atomic()` in `pythia/api/db_sync.py` stages each release download to `<dest>.tmp` (`data/resolver.duckdb.tmp`) then `os.replace()`s it onto `data/resolver.duckdb`. On the Render **persistent disk**, a crashed/interrupted download (or an older code path) left `data/resolver.duckdb.tmp` behind as a **directory**, so `tmp_path.open("wb")` failed with `[Errno 21] Is a directory` on *every* 60s sync. `_maybe_refresh_db()` only logs `DbSyncError` as a `warning` and swallows it, so the API silently kept serving the DB it last downloaded (around the May 19 deploy) even though the June 1 HS Triage run had published a fresh DB to the `pythia-data-latest` release. Because `/data` is persistent, the bogus directory and the stale DB survived restarts/redeploys. **Diagnosis tip**: the publish chain (HS Triage → `publish_latest_data.yml` → release asset + `manifest.json`) can be fully healthy while the dashboard is frozen — verify the release asset `updated_at` and `manifest.latest_hs_run_id` first, then suspect the API sync. Fixed by: (1) `download_db_atomic()` now self-heals — it removes any pre-existing temp path (`shutil.rmtree` if a directory, else `unlink`) before writing, and raises a clear `DbSyncError` if the destination itself is a directory; (2) sync-health observability — `db_sync.py` records `_LAST_SYNC_ERROR`/`_LAST_SYNC_OK_AT`/`_LAST_SYNC_ATTEMPT_AT` and the manifest key of the on-disk DB (`_LAST_DOWNLOADED_KEY`), exposed via `get_sync_status()`. `/v1/version` now includes a `sync_status` block and `/v1/health` flips to `{"status":"degraded","reason":"db_sync_failing"}` (still HTTP 200) when the last sync errored or the on-disk DB drifted behind the release. **Manual recovery if it recurs**: on Render, `rm -rf data/resolver.duckdb.tmp`, then `POST /v1/admin/force_sync?token=$FRED_DEBUG_TOKEN` (or restart). **Infra note**: atomic staging transiently needs a *second* copy of the DB on disk, so the `/data` disk must be sized to ≥ 2× the DB (~910MB and growing) to avoid `ENOSPC` as a future variant.
- **API `_refresh_latest_runs` used cached connection** (fixed): `_refresh_latest_runs()` in `pythia/api/db_sync.py` opened the DB via `duckdb_io.get_db()`, which caches connections process-wide by path. After `download_db_atomic` replaced the DB inode, the cached handle kept reading the old inode forever — leaving `_LATEST_RUNS` (hence `/v1/version`'s `latest_hs_run_id` / `latest_forecast_run_id`) frozen on pre-refresh runs despite a successful download. Fixed by opening a fresh direct `duckdb.connect(..., read_only=True)` each call and closing it in `finally`.
- **DuckDB WAL replay crash on startup** (fixed): After `_maybe_refresh_db()` replaced the DB file on disk while the old connection was still open, the stale `.wal` file from the old connection's `ensure_schema` run persisted. On next process restart, `duckdb.connect(read_only=False)` replayed the WAL which contained a duplicate `ALTER TABLE ADD COLUMN fetched_at`, crashing with `CatalogException: Column with name fetched_at already exists!`. Fixed by catching `CatalogException` in `_open_duckdb_connection()`, deleting the stale WAL file, and retrying the connection. Safe because the API's authoritative data comes from the synced DB file, not the WAL.
- **DuckDB WAL replay crash on artifact download** (fixed): Downloaded `pythia-resolver-db` artifacts could include stale `.wal` files, or WAL files were left behind between candidate iterations in the canonical DB discovery loop. DuckDB's WAL replay crashed with `InternalError: Failure while replaying WAL file … Calling DatabaseManager::GetDefaultDatabase with no default database set`. Fixed in two places: (1) `scripts/ci/db_signature.py` now calls `_remove_stale_wal()` to delete any `.wal` file before opening the DB; (2) all 11 workflow files that download and validate DB artifacts now explicitly `rm -f data/resolver.duckdb.wal` after copying the DB and before opening it.
- **ACAPS iso3 list values** (fixed): The ACAPS API sometimes returns `iso3` as a list instead of a string. All bulk-fetch functions in `pythia/tools/ingest_structured_data.py` (`_bulk_fetch_inform_severity`, `_bulk_fetch_risk_radar`, `_bulk_fetch_daily_monitoring`, `_bulk_fetch_humanitarian_access`, `_bulk_fetch_reliefweb`) now defensively coerce list values to strings before calling `.upper()`.
- **Adversarial checks / tail packs silenced by PYTHIA_WEB_RESEARCH_ENABLED=0** (fixed): The deprecated `PYTHIA_WEB_RESEARCH_ENABLED=0` flag (which disables the old question-level web research pipeline) was also blocking `fetch_evidence_pack` calls in adversarial checks and hazard tail packs. Both now temporarily override the env var to `"1"` around their `fetch_evidence_pack` calls, so they work independently of the deprecated flag.
- **ACLED CAST expired token passthrough** (fixed): `get_access_token()` in `resolver/ingestion/acled_auth.py` now validates JWT expiry via `_jwt_is_valid()` before using environment-provided tokens. Expired tokens fall through to the refresh/password grant flow instead of being returned as-is.
- **ACAPS Humanitarian Access field names** (fixed): The ACAPS Humanitarian Access API does not return an `iso3` field in its response records (unlike INFORM Severity, Risk Radar, etc.). The bulk fetcher in `pythia/tools/ingest_structured_data.py` tries multiple field names (`iso3`, `iso`, `country_iso3`, `country_code`, `country_iso`) and falls back to a nested `country.iso3` dict lookup. A sample-record-keys log line is emitted on first record to aid debugging if the schema changes again.
- **conflictforecast.org wrong value column** (fixed): `_transform_csv()` in `resolver/connectors/conflictforecast.py` was selecting the `_target` column (ground truth, NaN for future periods) instead of `_all` (combined model forecast), producing 0 rows. Fixed by adding suffix-priority column selection (`_all` > `_text` > `_hist`, skip `_target`/`_naive`), a Backendless metadata skip set, and a median-value sanity check (onset metrics only).
- **NMME regionmask low country count** (fixed): `resolver/ingestion/nmme.py` used `countries_110` (coarsest Natural Earth resolution), which resolved only ~12 countries. Changed to `countries_10` (highest resolution) with `natural_earth_v5_1_2` preferred over `v5_0_0` for 170+ country coverage.
- **IDMC displacement hazard code mismatch** (fixed): `_load_idmc_conflict_flow_history_summary` and `_build_conflict_base_rate` in `forecaster/cli.py` filtered by `hazard_code = ?` (passing `'ACE'`), but IDMC writes data with `hazard_code='IDU'`. Fixed to use `IN (?, 'IDU')` to match both.
- **Gemini SPD timeouts** (fixed): Gemini Flash and Pro SPD calls timed out at 90s/120s respectively. Raised both to 300s in `forecaster/providers.py` (env-overridable via `PYTHIA_GOOGLE_SPD_TIMEOUT_FLASH_SEC` / `PYTHIA_GOOGLE_SPD_TIMEOUT_PRO_SEC`). HS triage timeout remains at 120s.
- **ACLED OAuth credential whitespace** (fixed): `_resolve_password_creds()` and `_resolve_refresh_token()` in `resolver/ingestion/acled_auth.py` read env vars without `.strip()`, so trailing whitespace/newlines from GitHub Secrets caused HTTP 415/400 on the OAuth password grant. Fixed by adding `.strip()` to all credential env var reads (`ACLED_USERNAME`, `ACLED_PASSWORD`, `ACLED_REFRESH_TOKEN`). Also added debug logging of the username in `_password_grant()`.
- **ACLED read timeout kills resolver_update Phase 1** (fixed): `ACLEDClient._fetch_page` in `resolver/ingestion/acled_client.py` had a 30s timeout and only retried on HTTP 429 / 5xx, not on `requests.exceptions.Timeout` / `ConnectionError`. A read timeout during `monthly_fatalities` (all-country query via `resolver/cli/acled_to_duckdb.py`) propagated uncaught and failed Phase 1 of `resolver_update.yml`. Fixed by wrapping `session.get` in try/except for `requests.exceptions.Timeout` and `requests.exceptions.ConnectionError`, retrying with exponential backoff (`min(60, 2^attempt)` seconds) up to `max_retries`, then re-raising. Also raised the default timeout from 30s to 120s in both the `ACLEDClient` constructor and `resolver/ingestion/config/acled.yml` to accommodate large all-country queries.
- **acled_political missing from default ingest** (fixed): `acled_political` was placed in `_SOURCE_ALIASES` (with a duplicate entry) instead of `_SOURCE_GROUPS` in `pythia/tools/ingest_structured_data.py`, so it never ran in default (all-sources) mode. Moved to `_SOURCE_GROUPS` and removed duplicates.
- **Debug bundle health check false statuses** (fixed): In `scripts/dump_pythia_debug_bundle.py`, HS Grounding check was reading wrong data source (now uses `hs_web_research_rows`), and Research Grounding reported FAIL when the retriever was intentionally disabled (now checks `retriever_enabled` flag).
- **CrisisWatch Cloudflare block** (fixed): crisisgroup.org is behind Cloudflare, returning 403 to programmatic fetches including Gemini grounding's internal fetcher. The old `site:crisisgroup.org` query in `crisiswatch_horizon.py` produced no results. Redesigned as `crisiswatch.py`: primary source is now the Playwright-scraped JSON file (`horizon_scanner/data/crisiswatch_latest.json`), with Gemini grounding as fallback (only attempted when JSON is missing/empty). Expanded injection from ACE-RC-only to ACE RC + triage + SPD prompts. Data persisted in the `crisiswatch_entries` DuckDB table. **Resolved for CI too (July 2026)**: the refresh was un-manualized by switching CI acquisition to the Wayback Machine (`--source wayback`) — the page is server-rendered, so an archive.org snapshot contains all entries and no browser is needed (see the ICG CrisisWatch section above).
- **CrisisWatch empty raw_text from fetch_via_gemini** (fixed): `_fetch_on_the_horizon()` and `_fetch_global_overview()` called `fetch_via_gemini()` and tried to extract text via `pack.get("markdown") or pack.get("raw_text")`, but `fetch_via_gemini` puts content into `pack.recent_signals`/`pack.structural_context` (not `markdown`/`raw_text`), and its internal JSON parser discards CrisisWatch's custom schema keys (`conflict_risks`, `countries`). Fixed by replacing `fetch_via_gemini` with a direct Gemini API call (`_call_gemini_grounding`) that returns raw text for CrisisWatch's own parsers.
- **Gemini 2.5 Flash Lite retired**: Replaced `gemini-2.5-flash-lite` with `gemini-2.5-flash` as the default grounding model across the system (`DEFAULT_GEMINI_CANDIDATES` in `gemini_grounding.py`, `_GEMINI_MODEL_CANDIDATES` in `crisiswatch.py`, cost entries in `model_costs.json` and `llm_logging.py`, fallback reference in `regime_change_llm.py`).
- **ACLED client silent stdout** (fixed): `acled_client.py` `main()` produced no stdout on skip, error, or empty-data paths, so `run_connectors.py` (which parses stdout for `rows=(\d+)`) reported 0 rows with no diagnostics. Fixed by adding `print(f"wrote {OUT_PATH} rows=...")` on all four exit paths in `main()`, upgrading `collect_rows()` error logging from `dbg()` to `LOG.warning()`, adding `_write_run_summary()` on the exception path, and adding a diagnostics JSON fallback in `run_connectors.py` that reads `acled_client_run.json` when the regex finds nothing. `acled_auth.py` `get_access_token()` also now emits `print("[acled_auth] ...")` at each auth stage (env token, refresh grant, password grant, exhausted) for CI log visibility regardless of `RESOLVER_DEBUG`.
- **IDMC double-run in backfill workflow** (fixed): IDMC ran twice in `resolver_update.yml` — once in the dedicated HELIX API step and again inside `run_connectors.py`. Fixed by adding `RESOLVER_SKIP_IDMC: "1"` to the "Run connectors" step env block.
- **Calibration advice dual-constraint failures** (fixed): `_upsert_advice()` in `pythia/tools/generate_calibration_advice.py` failed repeatedly due to the `calibration_advice` table having both the original 3-column PK `(as_of_month, hazard_code, metric)` and the newer 4-column unique index `ux_calibration_advice (as_of_month, hazard_code, metric, model_name)`. Root cause: the `CREATE TABLE` DDL in `schema.py` defined the 3-column PK, and **DuckDB does not support `ALTER TABLE DROP CONSTRAINT` for PRIMARY KEY constraints** — all `DROP CONSTRAINT` attempts failed silently regardless of constraint name. Fixed by **recreating the table**: `_migrate_calibration_advice_pk()` checks `information_schema.table_constraints` for a PK, and if found, uses CTAS to copy data into a temp table, `DROP TABLE` on the original (which cascades all dependencies including the PK — `ALTER TABLE RENAME` is also blocked by `DependencyException`), creates a new table without a PK, copies data back with column-safe SELECT (handling missing columns and NULL model_name), drops the temp table, and creates the 4-column unique index. The `CREATE TABLE` DDL in `schema.py` was also changed to `PRIMARY KEY (as_of_month, hazard_code, metric, model_name)` so fresh DBs never get the old PK. The upsert uses `INSERT INTO ... ON CONFLICT ... DO UPDATE SET`, and `_seed_default_advice` uses `ON CONFLICT ... DO NOTHING`.
- **Calibration advice hardcoded bucket thresholds** (fixed): `_bucket_case_sql()` in `generate_calibration_advice.py` hardcoded threshold values (e.g. `10000, 50000, 250000, 500000` for PA) that duplicated the canonical `PA_THRESHOLDS`/`FATAL_THRESHOLDS` lists from `compute_scores.py`. The imported constants `_bucket_index`, `PA_THRESHOLDS`, `FATAL_THRESHOLDS` were unused. Fixed by deriving the SQL `CASE` expression dynamically from the canonical threshold lists. Removed unused `_bucket_index` import.
- **Calibration advice silent exception swallowing** (fixed): Multiple `except Exception: pass` blocks in `generate_calibration_advice.py` (`_table_exists`, `_row_count`, `_ensure_findings_json_column`, `_migrate_calibration_advice_pk`) silently swallowed errors, making real DB connection failures or schema issues look like empty data. Added `LOGGER.warning` / `LOGGER.debug` to all critical silent exception paths.
- **Calibration workflow manual dispatch broken** (fixed): `compute_calibration_pythia.yml` used `github.event.workflow_run.id` to download the DB artifact, which is empty on `workflow_dispatch` (manual trigger). Replaced with a two-path strategy: (A) if triggered by `workflow_run`, download from the triggering run; (B) on manual dispatch or fallback, use canonical DB discovery (searches recent successful runs from Compute SPD Scores, Compute Calibration, Horizon Scanner Triage, Ingest Structured Data, and Resolver Update workflows).
- **Calibration workflow stuck on March "repaired DB"** (fixed): `compute_calibration_pythia.yml` had a hardcoded `FORCE_RUN_ID="23197624903"` (a one-off "Upload Repaired DB" run from 2026-03-17) that ran BEFORE Path A's triggering-run download and called `exit 0` on success. Every calibration run therefore downloaded the ancient March DB (facts_resolved=3,888, max created_at=2026-03-15), computed calibration on it, and uploaded it as the new `pythia-resolver-db` artifact. `publish_latest_data.yml` then overwrote the release with this stale DB — reverting the dashboard every time calibration ran after Resolver Update. Symptoms: dashboard Resolver page showed "No data" for GDACS/FEWS NET/IPC API and "last updated 2026-03-15" for IFRC/IDMC/ACLED even after Resolver Update succeeded with ~48K rows. Fixed by removing the `FORCE_RUN_ID` block entirely; Path A (triggering workflow_run download) and Path B (canonical discovery) now work as originally documented. Also added `Resolver Update` to the Path B candidate list.
- **Publish workflow can overwrite newer release with stale DB** (fixed): `publish_latest_data.yml` accepted any `run_id` (manual dispatch) or `workflow_run` trigger and uploaded the artifact straight to the release with `--clobber`, with no check that the new DB actually contained the post-pipeline tables already present in the release. Concretely: a manual `publish_latest_data` dispatch with `run_id=<Resolver Update>` (which only contains `facts_resolved`, no `resolutions`/`scores`) silently overwrote a freshly-published Calibration DB, so the dashboard's `/v1/diagnostics/resolution_rates` endpoint returned 0% scored across every (hazard, metric) and the Performance page's Resolution Coverage Summary showed `0/N questions` for everything — even though `compute_resolutions` had successfully written rows earlier in the day. The auto-trigger from `Resolver Update` has the same shape: it fires before `compute_resolutions` runs, so it would also overwrite a more complete release. Fixed by adding a "Regression guard" step in `publish_latest_data.yml` that downloads the current release DB (if any), counts rows in `resolutions`, `scores`, `bucket_centroids` (excluding seed wildcards `hazard_code='*'` and rows with NULL `as_of_month`), `calibration_weights`, and `calibration_advice` in both DBs, and aborts the publish when the new DB has strictly fewer rows than the current release in any of these tables. A `force_publish` workflow_dispatch input bypasses the guard for intentional rollbacks. The publish workflow also now stamps these counts into `manifest.json` under `table_counts` so the regression guard and downstream debugging can see at a glance whether the published DB has post-pipeline data. Missing tables in the new DB count as zero (regression); missing tables in the old DB are skipped (first-time publish or pre-existing schema gap).
